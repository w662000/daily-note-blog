# 技术点 · daily-publish（多端内容分发流水线 · 幂等 / 限流 / 失败兜底）

> 对应项目轴 Handoff：`2026-07-22-handoff-daily-publish.md`
> 目的：从该项目提炼**可复用技术资产**——「一份内容 → 多端自动分发」的流水线设计、第三方 API 的成功判定与限流治理、幂等与失败兜底策略、本机定时与云端定时的边界。任何"日报/周报/文章自动分发"场景可直接复用。

## 一、技术选型

| 选型项 | 选定 | 落选 | 依据 |
|---|---|---|---|
| 博客端 | **GitHub Pages + Jekyll（`daily-note-blog`）** | Gridea Pro 单独承担 | push 即自动构建上线，彻底消灭"手动点同步"（T1） |
| 知识库端 | **语雀 v2 API** | 网页手工粘贴 | 有开放 API，可脚本化（T0 有官方 API；限流行为 T1 实测） |
| 浓缩版端 | **Gridea Pro（写文件）** | 直接调 API | Gridea 无开放发布 API，只能写 `posts/*.md` 待用户点同步（T1） |
| 说说端 | **Ech0（本地 Docker）** | — | 7-23 已从自动发布链路**移除**，仅保留本地运行（T1） |
| 语雀调度位置 | **本机 23:35 定时任务** | GitHub Actions 云端 23:59 | 云端 Actions 定时有十几分钟延迟，且早期误判为"未发布"；本机直发更可控（T1，7-24 日志） |
| 传输库 | **裸 `requests.post` + 强制不走代理** | `requests.Session` | Session 在该环境下会吞请求返回空；环境代理会导致连不上语雀（T1） |
| 版本与推送 | **git + `gh` CLI** | 自建 API 上传 | 内容天然适合版本化；push 失败不丢内容（T1） |
| 脚本语言 | **Python** | PowerShell/bat | 跨端 API 调用 + 文件生成 + 幂等逻辑更好写（T1） |

## 二、实施要点与关键技术

1. **API 成功判定必须按真实响应结构写**（T1，踩过两次）：
   - 语雀 v2 API **成功响应里没有 `status` 字段**，结构是 `{"data":{...},"meta":{...}}`；
   - 早期按 `status` 判定 → 明明发布成功却报 FAIL；
   - 正确判据：**HTTP 200 且 `data.id` 存在**；
   - 通用教训：**先把一次真实成功响应打印出来，再写判定逻辑**，不要按想当然的字段名写。

2. **环境代理必须显式关闭**（T1）：`requests` 默认读取环境变量 `HTTP_PROXY`（本机指向一个已死的本地代理端口）→ 请求语雀直接失败。修法：`requests.post(..., proxies={"http": None, "https": None})` 强制直连。**凡是脚本调国内 API，先确认是否被环境代理劫持。**

3. **限流治理靠"单一通道"而非重试**（T1）：本地与云端双发会顶满语雀 token 额度导致连续 429。解法不是加重试，而是**把语雀收敛到唯一发布通道**（先云端 Action，后改本机 23:35），主脚本默认跳过语雀（仅当 `WB_LOCAL_PUBLISH_YUQUE=1` 时强发）。同时云端脚本保留为冗余备份，靠幂等保证重复触发无害。

4. **push 失败不致命的设计**（T1）：`git_commit_push` 失败只提示、不抛错——内容已经落进本地仓库，等网络/`gh` 就绪后下次 push 即生效。另加 `pull --rebase` 重试抵抗 fast-forward 拒绝。**这是"离线兜底"的核心：把不可靠的网络动作放在可靠的本地动作之后，且不让前者失败回滚后者。**

5. **不同工具走不同 egress**（T1，反直觉但重要）：沙箱环境里 Bash/Python 抓外网永远 `HTTP 000`（rc=35），但 `git push` 走另一套 egress 是通的。**不要因为 `curl` 测不通就断定"这台机器不能联网"。**

6. **静态博客的"未来文章"陷阱**（T1）：Jekyll 默认排除 `date` 晚于构建时间的文章。日报 date 写当天 23:30，构建时刻在其之前 → 文章消失。修法：`_config.yml` 加 `future: true`。

7. **草稿标记与幂等去重**（T1，同款坑踩过两次）：
   - Gridea 的 `published: false` 永不发布，脚本产出的 frontmatter 必须写 `published: true`；
   - 脚本生成稿与用户手动草稿若 `title` 相同，Gridea 会显示两份 → `gen_gridea()` 加幂等防御：扫描 `posts/*.md`，凡 `title == GRIDEA_TITLE` 且文件名 ≠ 目标文件名的一律删除。
   - **幂等的正确含义是"跑 N 次结果与跑 1 次一致"，包含清理自己上次的残留。**

8. **排序语义要按目标平台的排序键设计**（T1，7-22 日志）：Gridea 按 `createdAt` 降序排。日报固定用内容日期 `00:00:00`（保证按天有序），普通文章用真实发布时间（保证新文章排在当天日报之上）。**同一时间字段承载两种语义时，用取值约定区分，而不是加字段。**

9. **批量补历史内容必须显式传时间戳**（T1，7-22 日志的 Ech0 案例）：不传创建时间 → 全部落在同一秒 → 平台回退按 rowid 排序 → 顺序错乱。补历史时一律显式赋各条内容的真实时间戳。

10. **云端定时的能力边界**（T1）：GitHub Actions 跑在云端，**能调云 API（语雀）、能推仓库（博客），但碰不到本机 `localhost` 服务和本地文件目录**（Gridea、Ech0）。所以链路必然是「云端管两端 + 本机管两端」的混合模式，而不是全云端。

11. **云端定时的延迟与误判**（T1，7-24 日志）：GitHub Actions 的 cron 有十几分钟不确定延迟，曾据此误判"昨日未发布"（实际 00:12 已成功）。**判断"是否发布失败"要看平台侧结果，不要看本地时钟到点没到点。**

12. **Secrets 与空串兜底**（T1，7-26 日志）：GitHub Actions 引用不存在的 Secret **不报错、注入空串**；脚本必须对空串做校验兜底。另外排查 Actions 失败要展开 step 内部日志——顶部 Annotations 摘要里 Secret 被 `***` 打码，看不到真实错误。

13. **多副本脚本的同步维护负担**（T1）：同一脚本存在多份副本（主目录、自动化专用副本、Hermes 兜底副本、各 agent 的 memory/rules 目录、GitHub 仓库内同源脚本）。改动后必须逐份同步，否则会出现"改了没生效"。这是该架构公认的代价，需在文档里显式列出副本清单。

14. **主题变量共享**（T1，7-26 日志）：博客暗/亮主题改写 `_layouts/default.html`，`:root` 用暗色变量、`.theme-light` 用亮色，与既有站点**共用同一个 `localStorage` 键**（`flavor-theme`）实现跨站一致。做"视觉统一"必须逐项 grep 目标站真实最终颜色做对照表，不能自己发明配色（曾因此把标题写成暗绿）。

## 三、模块职责划分

- **生成层（`publish_daily_summary.py`）**：把机器日志转成人读总结，是内容的**唯一生产者**；默认跳过语雀，避免与专用通道抢额度。
- **仓库同步层（`sync_logs_to_github.py`）**：把总结复制到语雀源仓库（`workbuddy-daily-note/summaries/`）和博客源仓库（`daily-note-blog/_posts/`）并 push，只管"进仓库"。
- **交接文档流水线（`handoff/handoff_flow.py`）**：归档 + Gridea + 博客 + 语雀直连，带会话感知（`handoff_config.json`）与幂等去重。
- **语雀专用通道**：单一发布口，独占额度。
- **Gridea 生成器**：只写文件，不负责上线（上线由用户在客户端点同步）。
- **兜底副本层（`~/.hermes/memories/` 下的脚本副本 + paused 定时任务）**：主执行器不可用时的接管道具。
- **定时调度层**：23:30 生成+推仓库、23:30 handoff 发布、23:35 Gridea 浓缩版、23:35 语雀本机发布；另有 failover/离线兜底时段。

一句话：**生成、入仓、发布、兜底四层分离，每个外部平台只有一个发布出口。**

## 四、如何选型（可复用的决策方法论）

- **端选型看"有没有 API + 能不能免手工上线"**：有 API 且能直接上线（语雀）→ 脚本直发；无 API 但吃文件（Gridea）→ 生成文件+人工一步；有 API 但价值低（Ech0）→ 果断从链路移除。**别为了"多一个端"承担长期维护成本。**
- **定时位置选型**：任务只碰云资源 → 可放云端（关机免疫，但有延迟）；任务要碰本机文件或 `localhost` 服务 → 只能放本机（关机则漏）。**先列任务触碰的资源清单，再决定跑在哪。**
- **限流场景的第一解法是收敛通道，不是加重试**：多入口并发是限流的根因，重试只会加剧。
- **成功判定要基于真实响应样本**：先打印一次成功响应再写判定，避免"发成功了却报失败"的假故障。
- **失败设计三原则**：本地动作先做（保住内容）→ 网络动作可失败（只提示）→ 下次运行自动补齐（幂等）。
- **幂等实现清单**：目标文件按确定文件名写（可覆盖）+ 清理同标题的历史残留 + 平台侧重复检测（已存在则跳过）。

## 六、技术结合点

- **单一发布通道 + 幂等脚本**：通道收敛解决限流，幂等解决"通道切换期间可能重复触发"。只收敛不幂等，切换那几天会重复发；只幂等不收敛，照样 429。两者配合才能既不重复也不被限流。
- **本地落盘 + push 失败不致命 + 下次自动补推**：三段构成一条"离线可用"的链路——网络状况从不影响内容生产，只影响上线时刻。这让整个系统可以在不稳定网络下长期无人值守运行。
- **云端定时（关机免疫）+ 本机定时（能碰本地资源）**：两者能力互补且互不覆盖，因此不是二选一而是分工。理解这一点后，"要不要全上云"这个问题自动消解。
- **`future: true` + 固定 `00:00:00` 时间语义**：前者让当天 23:30 的文章不被 Jekyll 判为未来文章，后者让多平台排序稳定。两个小设置合起来，才让"每天定时发布"这件事在静态站上成立。
- **兜底脚本副本 + paused 定时任务**：副本保证能力可迁移，paused 任务保证接管只需一次启用操作而非重新配置。这是"主执行器可被替换"的低成本实现。
- **主题变量共享（同一 localStorage 键）**：多个站点共用一个主题开关状态，用户在任一端切换、另一端自动一致——用一个约定键替代了跨站同步机制。
