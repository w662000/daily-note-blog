### 1.2 应该改（方向对，做法要换）

| # | 豆包主张 | 队长裁定 |

## 二、引擎选择（4 个）及实证依据

**选定：`brave` / `wikipedia` / `mojeek` / `baidu`**

| 引擎 | 理由 | 证据 |
|---|---|---|
| brave | 语义友好（独立索引，非 Google/Bing 代理）、中文覆盖好 | [C16] 存在；[E2][E3] 实测能出中文结果 |
| wikipedia | 中文维基，事实型断言的最佳来源；轻量 | [C16] 存在 |
| mojeek | 独立爬虫，**几乎不对机房 IP 限流**，是 brave 被限流时的多样性补充 | [C16] 存在 |
| baidu | 中文网络覆盖最好，直接满足「对中文网络环境支持好」 | [C16] 存在；[E8] 直连 302 有响应（非 Render IP，仅弱信号） |

**弃用**：google（从不加载）、bing（机房 IP 风险，且与既定决策冲突）、duckduckgo（实测持续超时 [E3][E4]）、github（与事实核查无关，省内存）。

**备选**（baidu 若被 Render 出口 IP 拦截时按序替换）：`360search` → `chinaso` → `sogou`，三者均已确认存在 [C16]。

**当前引擎健康度实测（2026-10-23）**：brave 当日第 2 次查询即被限流 [E5]，duckduckgo 持续超时 [E3][E4]。
也就是说现有 5 引擎里实际只有 bing 在稳定出中文结果——而 bing 正是要禁用的那个。
**这个缺口只能靠 baidu + Tavily 备用填补**，所以主备架构不是可选项而是必需品。

## 三、关键设计修正：放弃 `site:` 运算符，改为代码层域名过滤

[E4] 是决定性负面证据：`政策原文 … site:gov.cn` 该实例返回 10 条**全部来自 bing、
内容是 X(推特) A 股股评**的结果，与税务毫无关系。

结论：**任何依赖 `site:` 运算符的方案都不可靠**（多引擎对运算符支持不一致，
长中文查询下 bing 直接返回噪声）。

改为：
1. 查询词保持干净：`政策原文 <claim>`（不加任何 site: 从句）
2. 拿到结果后**在代码里按 host 后缀过滤**，只保留 `chinatax.gov.cn` / `mof.gov.cn` / `gov.cn`
3. 过滤后为空 → 显式记 `mismatch: true`，finding 写「未找到对应政策原文」，**不静默丢弃**
4. 过滤后有结果 → 只用这些官方站点摘要做数字核对

这比 Tavily 的 `include_domains` 更确定：它不依赖引擎是否支持某个运算符，
而是在我们自己的代码里做白名单，失败方向是"判否"而不是"放行"。

> 注意 host 匹配必须写 `host === 'gov.cn' || host.endsWith('.gov.cn')`，
> 不能写 `endsWith('gov.cn')`——否则 `notgov.cn` 会被误判为官方站点。

## 四、主备架构与接入设计（两个系统同源）

```
extractClaims(政策类插队)
   ↓
① SearXNG 主搜索（免费、无限次）
     query = 政策原文 <claim>
     结果 → 代码层按 POLICY_DOMAINS 过滤
     有官方结果 → 作为 finding 进入确定性数字核对
   ↓ 无结果 / 超时 / 5xx / 连续失败(熔断)
② Tavily 备用搜索（受日限 + 熔断保护，逻辑不变）
   ↓ 也无结果
③ 政策类：显式 mismatch:true；非政策类：跳过（不硬编证据）
```

**熔断器（豆包漏掉的关键一环）**：
- SearXNG 单次失败不熔断（Render 休眠很常见，一次失败很正常）
- 同一 `verifyClaims` 调用内连续 2 次失败 → 后续声明直接走 Tavily
- 进程级冷却：累计 3 次失败 → 5 分钟内不再尝试 SearXNG
- 目的：**避免冷启动期间把 Tavily 备用额度烧光**

**超时与重试**（吸收豆包 Python 示例）：
- SearXNG 超时 45s（覆盖 30–80s 冷启动的下界）、失败重试 1 次、间隔 12s
- Tavily 超时 20s、不重试（它有日限，重试是烧额度）
