# 技术点 · 常驻探测看板的错误归类，与多端自动发布链路的可靠性治理

> 对应项目轴 Handoff：`2026-08-01-handoff-model-speed-radar-看板-a-计划收尾与-handoff-自动发.md`
> 目的：从该项目提炼**可复用技术资产**——常驻守护进程的错误细分与前端一致性、多目标自动发布链路的时序与幂等设计。下次做任何"后台定时探测 + 网页看板"或"一份内容分发多平台"的系统，直接复用这套判定规则与护栏。

## 一、技术选型

| 选型项 | 选定 | 落选 | 依据 |
|---|---|---|---|
| 探测进程运行方式 | **系统级常驻（nohup / 无窗口后台）** | 框架后台任务句柄 | 后台任务句柄会被框架在对话轮次切换时回收，导致服务静默消失（T1，多次复现） |
| 探测语言/依赖 | **Python 标准库，零第三方依赖** | requests / FastAPI 等 | 守护进程要跨会话常驻、随时被人手动拉起，依赖越少启动失败面越小（T1） |
| 前端技术 | **原生 JS + 轮询（10s）**，无外部库 | 框架 + WebSocket | 离线可用、单文件可拷；轮询"有新数据才刷新"避免整页闪（T1） |
| 错误归类粒度 | **细分 `endpoint_mismatch` / `model_gone` / 限流 / 无额度** | 统一 `error` | 粗归类会把"模型活着但不接这个端点"误判成"模型下线"，直接导致误删条目（T1，栽过两次） |
| 发布链路时序 | **单串行任务，显式依赖** | 多任务靠时间间隔隐式串行 | 实测扫描要 144s 而间隔只给 120s，下游抢跑 24s，会读到写了一半的收件箱（T1） |
| 归档策略 | **全部目标端成功才归档，任一失败留箱** | 无条件归档 | 无条件归档会让次日补发扑空，容灾形同虚设（T1） |

## 二、实施要点与关键技术

### 探测侧

1. **温和拨测规则写进代码而不是写进文档**（T1）：串行执行、目标间隔 2.5 秒、每目标每轮只发 1 次、撞错立刻停不重试、限流冷却 2 轮、无额度冷却 6 轮、手动触发 5 分钟冷却、端口占用即退出防双实例、重启时距上次不足一个周期先等够再测。**曲线平滑靠"近 N 轮均值"，不靠多打几枪。**

2. **区分"路由级 404"与"资源级 404"**，这是错误归类的核心技术点（T1）：
   - 生成类探针命中路由级 404（典型响应体 `{"detail":"Not Found"}`）→ 归 `endpoint_mismatch`（接口不符）；
   - 对话类探针命中 404 → 归 `model_gone`（真下线）；
   - 生成类本就无对应端点 → 归 `model_gone`。
   - 辅助函数 `_is_route_404()` 靠响应体文案区分：`not found / 404 page` 属路由级；`model is not found / does not exist / no endpoints` 属资源级。

3. **HTTP 429 不等于限流**，要解析响应体业务码二次分类：无额度类（重试无用）与真限流类（可退避重试）必须分开，否则会对着没额度的目标无限重试（T1）。

4. **重归类历史数据靠改落盘 JSON，不靠重发请求**。每次调整分类规则后写一次性脚本重算已落盘数据，绝不为刷新看板重打接口（T1）。

5. **慢目标当天冷却**：连续 3 轮自身墙钟占用超过阈值（10s）的目标，当天剩余轮次跳过；**计时只算目标自身耗时，不把前一个目标的间隔算进来**，否则会误伤正常目标；状态落盘跨重启保留，次日自动重判（T1）。

6. **超时值要按真实失败模式定**。把连接超时从 45s 统一降到 10s 后，无法直连的一组目标从每轮白等 65 秒降到 10 秒（T1）。

### 前端一致性

7. **改了前端看不到效果 → 先想缓存**。曾出现"补丁在磁盘上是对的但界面还是旧的"，真因是浏览器缓存了旧 JS。解法：响应头加 `Cache-Control: no-store` + 静态资源版本号（如 `index.html` 版本号 `20260801c → 20260801d`）双保险（T1）。

8. **新增错误分类要同步四处**：分类逻辑、落盘字段、前端 `ERR_TAG` 映射、样式类（如 `.dead-item.mismatch` 琥珀色）。漏一处就出现"后端已分类、界面仍混在一起"（T1）。

9. **渲染函数兜底逻辑要单一出口**。同一份数据在三个渲染函数里各有一套兜底（一个无兜底、一个三级兜底、一个另一套），是已知技术债——正确做法是抽统一的分类函数单一出口（T1，当时评估为"加固非修复"暂缓）。

### 启动器（Windows）

10. **启动脚本的三处脆弱点**（T1，全部实际踩过）：
    - ① 固定 `sleep N` 后拉浏览器 → 首跑要加载大量配置与历史，端口没绑好就连，报"连接被拒绝"。**改成就绪轮询：确认端口真在监听才拉浏览器。**
    - ② 用可见 cmd 窗口挂守护进程 → 窗口一关服务就死。**改无窗口后台常驻。**
    - ③ 端口被占时静默退出 → 无任何提示。**改成启动前先查端口 + 全程写 launcher.log。**
11. **bat 文件编码是硬坑**：UTF-8 无 BOM 的中文回显被 cmd 按 GBK 读成乱码，乱码字符一旦撞上 bat 语法字符会导致**整行解析失败、后续命令全不执行**。根治办法是**回显纯 ASCII**（中文提示改英文），别指望 `chcp 65001` 救（T1）。
12. **Windows 上排查/收拾进程的命令**：Git Bash 没有 `pkill`；`taskkill` 有路径转换问题，要写 `MSYS_NO_PATHCONV=1 taskkill /PID xxx /F`；查监听用 `netstat -ano | grep :<port>`（T1）。

### 发布链路侧

13. **内容提取要吞完整子树**。提取函数原先只取同级标题下的直接内容，遇到有子标题的分节就只取到空行，导致下游稿件正文空白。修法：匹配到目标标题后，**继续吞入所有更深层子节，直到遇到同级或更高级标题**（T1）。

14. **标题必须携带内容日期而非运行时刻**。去重只看标题会导致同名稿件永久漏发；而用运行时刻打日期，跨零点补发会标错（内容属前一天却标成当天）。正解：**从源文件名的日期前缀反解**（T1）。

15. **调度器有约 5 分钟提前量**（标称 23:00 实际 22:55 起跑，历次稳定）。排查和排程都要换算（T1）。

16. **"无源可发"被记成成功 = 监控失明**。链路 48 秒跑完、日志全绿、实际零产出。应返回非零码或至少 WARN（T1，已知缺陷）。

17. **落盘 ≠ 上线**。静态站点生成器场景下，写进 `posts/*.md` 只是源稿落盘，真正上线要看 `output/post/<slug>/` 有没有渲染产物。以落盘判成功并立即归档，会绕过失败留箱机制（T1）。

18. **"收件箱为空"不能当健康信号**：它同时兼容"全发完"和"无源可发"两种相反状态（T1）。

19. **不同目标端的渲染能力差异极大，一份内容发多端不可能**（T1，3 轮修复实测）：纯 Markdown 型平台吃 HTML 标签会让整块表格崩掉；论坛型平台 HTML 被转义、纯文本最安全；部分论坛不支持表格标签；只有博客类能吃完整交互 HTML。→ **必须为每端单独生成格式。**

20. **部分平台的文档原始格式不可逆**：创建时不是 markdown 的文档，后来改格式字段也不会重新触发渲染引擎，只能删除重建（T1）。

## 三、模块职责划分

- **守护进程**：只负责"按周期发探针 + 落盘原始结果 + 错误归类"，不负责展示。
- **内置 HTTP 服务**：只负责静态资源与数据接口，附带缓存控制头。
- **前端**：只负责渲染与轮询，不做二次业务判定（分类结论应由后端给全）。
- **启动器**：只负责"探测端口 → 拉起进程 → 就绪轮询 → 打开界面 → 记日志"，任何一步失败都要留痕。
- **扫描阶段**：只负责"发现项目文档 → 生成待发条目 → 写入收件箱"，硬拒非法输入（如每日汇总类文档）。
- **发布阶段**：只负责"按目标端分别生成格式 → 逐端投递 → 检查返回值 → 全成功才归档"。
- **巡检任务**：独立于主链，次日按幂等规则复核各端是否真上线，只补缺不重发。

## 四、如何选型（可复用的决策方法论）

- **常驻服务的进程模型怎么选**：凡是"要跨会话/跨对话轮次活着"的，一律走系统级常驻 + 日志文件监控，不要用任何框架托管的后台句柄。
- **错误分类粒度取决于下游动作**：如果分类结果会触发"删除条目"这类不可逆动作，就必须细分到能区分"目标不存在"和"这条路走不通"。粒度不够 = 误删。
- **自动化链路的串行怎么保证**：先实测每一棒的真实耗时，再决定是加锁文件、合并成单任务，还是回调触发。**绝不用"估个间隔"来隐式串行。**
- **幂等设计的判定点要选在最终态**：判"成功"要看目标端的最终可见产物，不能看中间产物（源稿落盘、返回码为 0 都不算）。
- **多端分发要先做能力矩阵**：上线前把每个端的渲染能力实测一遍（是否吃 HTML、是否支持表格、是否转义），矩阵定下来再写生成器，比边发边改省 3 轮返工。
- **观察期 vs 立即修**：病根已堵死、剩下的属加固而非修复、且没有回归测试保护时，可以进观察期——但必须**明确写出"出现即动手"的触发信号**，否则观察期等于遗忘。

## 六、技术结合点

- **错误细分 + 前端配色**：后端把 `endpoint_mismatch`（接口不符）和 `model_gone`（已下线）分开，前端用两种颜色呈现，人在界面上一眼就能判断"该修配置"还是"该删条目"——两者缺一，分类白做或界面误导。
- **就绪轮询 + 端口自检**：启动器轮询端口才拉界面，守护进程自检端口占用即退出，两者配合同时解决了"打开太早连不上"和"双击多次起多个实例"两个相反的问题。
- **无缓存头 + 资源版本号**：单用版本号，老浏览器仍可能命中强缓存；单用 `no-store`，静态资源全不缓存伤性能。两者叠加才既能保证补丁即时生效又不牺牲太多。
- **失败留箱 + 次日巡检**：留箱保证源不丢，巡检保证缺被发现并幂等补齐。只做留箱会积压，只做巡检会因源已归档而补不回来。
- **单串行任务 + 内容日期标题**：串行消除时序漂移，内容日期消除跨零点错标。两者一起才让"每天一份、不重不漏"成立。
- **温和拨测 + 离线重算**：探测端克制不重打，分类规则变更时靠脚本重算历史数据——既保住了数据完整性，又守住了配额红线，这是"频繁迭代分类规则"能成立的前提。
