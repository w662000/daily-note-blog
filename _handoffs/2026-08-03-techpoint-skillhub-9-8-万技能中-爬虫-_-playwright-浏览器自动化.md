# 技术点 · 超大规模 JSON 数据的多桶关键词筛选、字段增强与去重报告生成

> 对应项目轴 Handoff：`2026-08-03-handoff-skillhub-9-8-万技能中-爬虫-_-playwright-浏览器自动化.md`
> 目的：从该项目提炼**可复用技术资产**——在 10 万级条目的单个大 JSON 上，怎么用"双桶关键词 + 交集"精准筛选、怎么给命中条目做长度分级的字段增强、怎么生成"既全量机器可读又可读报告"的产物。这是上篇"抓下来建站"的下游提炼方法论，做调研/检索数据底座时直接复用。

## 一、技术选型

| 选型项 | 选定 | 落选 | 依据 |
|---|---|---|---|
| 筛选对象 | **直接读已落盘的 `skillhub_all.json`（154MB）** | 重新发请求抓 | 数据源已在手，重抓既浪费额度又可能漂移（T1） |
| 匹配方式 | **逐条拼装字段为 blob 再 `re.search`** | 结构化字段逐项比对 | 候选字段多（name/description/tags/category/subCategories/slug），拼成一串后单条正则更简洁（T1） |
| 桶设计 | **双桶（A 浏览器自动化 / B 爬虫）独立命中 + 取交集** | 单关键词表 | 单表误报极高；交集（既命中 Playwright 又命中爬虫）才是"最精准"子集（T1，实测对比） |
| 字段增强 | **`official_desc` 三级长度处理** | 一律摘要或一律全文 | 引用官网必须保真：<200 字照搬、200–500 字全文、>500 字截断并标注（T1） |
| 报告生成 | **交集全列 + 单桶 TOP N + `seen` 集合去重** | 全量逐条展开 | 全量 5000+ 条全展开既不可读也不可维护；交集优先 + TOP 截取兼顾覆盖与可读（T1） |
| 机器可读产物 | **与报告并行的 `.json`（含命中桶标记 + `desc_len`）** | 只给报告 | 报告给人看，JSON 给下游灌库/二次筛选用，两者分轨（T1） |

## 二、实施要点与关键技术

1. **关键词桶的口径决定误报率。** 第一版用了"下载/验证/登录/代理/识别"这类通用词，误报 16,773 条；收窄成爬虫语境专用词后降到 366 条，噪音清干净了。→ **桶的选取宁可窄、宁可漏，别用通用词撑量**（T1）。

2. **双桶关键词清单（本项目实测有效）**（T1）：
   - **A 桶（Playwright / 浏览器自动化 / headless）**：`playwright`、`puppeteer`、`selenium`、`浏览器自动化`、`浏览器驱动`、`网页自动化`、`headless browser`、`browser automation`、`浏览器测试`、`浏览器操控`
   - **B 桶（爬虫 / 抓取 / 采集）**：`爬虫`、`crawl`、`scrap`、`抓取`、`爬取`、`采集`、`数据采集`、`网页抓取`、`网络爬虫`、`网站抓取`、`内容抓取`、`网页采集`、`网页数据`

3. **拼装 blob 再正则的写法**：把 `name/description/tags/category/subCategories/slug` 拼成一段文本，对两个桶各做一次 `re.search`（大小写不敏感），记录命中 A / 命中 B / 命中两者。单条一次性判定，比逐个字段判等省事且不容易漏字段（T1）。

4. **排序键要稳**：命中集合内部按 `(stars, installs, downloads)` 排序，保证同一批数据多次运行结果一致、可复现（T1）。

5. **`official_desc` 三级处理**（T1）：
   | 原始长度 | 处理 |
   |---|---|
   | `< 200` 字 | 原样照搬（不注水，符合"引用官网"） |
   | `200–500` 字 | 全文 |
   | `> 500` 字 | 截断至 500 字并追加标注 |
   | 空介绍 | 标"官网未提供介绍" |

6. **验证要"重跑一致性"**。用与原报告**完全一致的关键词**重跑，结果必须严格一致（本项 5,608 / 676 / 4,681 / 251），以此确认"增强的是同一批 skill，没偷偷换集合"（T1）。JSON 结构也要校验五键齐全（total / bucket_A_only / bucket_B_only / both / matches）。

7. **报告去重合并**：交集 251 全列 + Playwright 高分 TOP40 + 爬虫高分 TOP20，用 `seen` 集合按 `slug` 去重，避免重复展开（T1）。

8. **命中分布（本项目实测）**（T1）：
   | 桶 | 命中数 |
   |---|---|
   | A 桶单独（Playwright 类） | 676 |
   | B 桶单独（爬虫类） | 4,681 |
   | 交集（Playwright + 爬虫，最精准） | 251 |
   | 合计去重 | 5,608 |

9. **收窄可继续做**：交集 251 个可进一步按 `stars≥50` 或 `verified` 认证过滤，得到可直接落地的精选清单（T1，已提出未做）。

## 三、模块职责划分

- **数据源（静态）**：`skillhub_all.json` 作为不可变输入，筛选逻辑只读取不改写。
- **筛选引擎**：只负责"读 blob → 双桶判定 → 打命中标记"，输出结构化中间结果（含桶标记与 `desc_len`）。
- **字段增强器**：只负责按长度三级处理 `official_desc`，不改动其他字段。
- **报告生成器**：只负责"交集全列 + 单桶 TOP N + 去重"，产出可读 `.md`。
- **机器可读产物**：与报告同源生成，供下游灌库或二次筛选，字段与报告对齐。

## 四、如何选型（可复用的决策方法论）

- **大规模 JSON 筛选要不要上数据库**：单文件 10 万级、一次性调研、不需要持续查询 → 直接 Python 内存遍历更快，不必先建库（T1）。
- **关键词桶怎么设计**：先想清楚"我要的是哪个交集"。A 桶定场景（如浏览器自动化），B 桶定用途（如爬虫），交集才是精准子集；单桶误报靠收窄词表压制。
- **引用型字段增强的铁律**：只要产物标注"引用官网"，就必须保真——短的别注水、长的明确截断标注、空的明确标无。注水或静默截断都会让"引用"失真，引发合规与可信度问题。
- **报告与机器产物分轨**：人读的报告追求"可读 + 覆盖关键"，机器产物追求"全字段 + 可重放"。两者从同一中间结果生成，保证一致。
- **可复现是验证底线**：筛选逻辑的任何改动，必须能用相同输入跑出相同输出。用"重跑一致性"一次性锁定集合，避免"以为在增强原集合、实际换了集合"。

## 六、技术结合点

- **双桶判定 + 交集优先**：单桶给量、交集给精度，报告把交集全列、单桶 TOP 补充，既保证"最准的都看到"又不丢失"次准的"。
- **blob 拼装 + 三级字段增强**：拼装让单条正则覆盖所有字段，三级处理让增强结果既保真又可纳入报告篇幅。两者配合，"引用官网"才既快又可信。
- **重跑一致性 + 机器产物校验**：一致性锁定集合范围，五键校验锁定结构完整，两个校验一起做才敢把报告当权威交付物。
- **报告分轨 + 同源生成**：报告给决策者看，JSON 给下游系统吃，两者同源自中间结果，杜绝"报告说有、程序读不到"的偏差。
- **静态数据源 + 内存遍历**：跳过建库步骤直接遍历，让"调研型"筛选成本极低、可随手重跑——这正是能反复迭代关键词桶的前提。
