# 多智能体 PDCA 协作工作法（通用思维骨架）

> **原点**：用户希望"发出任务后派出 3-5 个 agent 助手，按 PDCA 原则先拆分任务、摸清底细——例如设计涉及微信爬取时，至少一个 agent 负责调查微信风控机制与避坑点，然后规划方案（一个个爬还是多线程、爬多少条落盘验证、间隔多久），再灌库，多个 agent 分工执行；并专门有 1 个 agent 负责找 plan 的漏洞与毛病，及时改进方案，然后再正式 PDCA 执行。"
>
> **目的**：治"懒作为"——先搞清底细、先暴露方案漏洞，再动手。避免"一头扎下去猛干、连撞 3 次才去查"的翻车。

## Overview

PDCA 不是主 agent 一个人串行走完，而是**用 3~5 个 agent 并行分工**，且**强制插入一个"挑刺 agent"在动手前审 plan**。顺序是：先拆 + 先查 + 先规划 + 先挑刺 → 定稿 → 再正式 Do。

Hermes 下的落地映射：
- 派子 agent → 用 `delegate_task`（每个角色一个独立子 agent，带完整自洽的 prompt）。
- 任务清单/看板 → 用 `todo` 工具建卡、指派、标状态、限 WIP。
- 联网检索 → `web_search` / `web_extract`（遵守"先搜再判"）。
- 读官方文档 / 本地文件 → `read_file` / `search_files`。
- 落盘验证 / 交付 → `write_file` 写本地文件与记忆，作证据与交接。
- 跨 skill 引用 → 通过 `metadata.hermes.related_skills` 与本技能联合加载（如 `agent-plan-router`、`plan`）。

## When to Use

满足任一即默认进入本工作法：
- 多步骤（≥3 个实质步骤）且跨多个子系统 / 文件。
- 涉及**陌生领域 / 外部平台 / 第三方 API**（微信爬取、云部署、支付、风控、数据库迁移等）。
- 需要"先摸清机制 / 避坑"才能动手的设计类任务。
- 用户明确说「按 PDCA」「多 agent」「分工」「挑刺」。

**Don't use for**：简单问答、单文件小改、纯查询、用户只要一句话结论。

## Trigger 与角色编排（每次 3~5 个，角色固定）

| 角色 | 数量 | 职责 | 关键产出 |
|---|---|---|---|
| 1. 调查员 Investigator | **≥1**（按陌生领域数，每个领域派 1 个） | 摸清任务底细：搜官方文档 / 社区实测 / **风控与限流机制** / 坑位清单 | 《领域机制与避坑清单》（每条结论附来源） |
| 2. 规划员 Planner | 1 | 基于调查产出方案：步骤拆分、技术选型、**节奏参数（逐个串行 vs 多线程 / 单次条数 / 间隔）**、落盘验证阈值、灌库与幂等 | 《执行方案 v1》 |
| 3. 挑刺员 Critic（红队） | **1（强制，不可省）** | 专找 plan 漏洞：未证伪假设、是否忽略平台限流、单点故障、验证能否证伪、是否有更简路径 | 《方案漏洞与改进建议》（逐条可改） |
| 4~5. 执行员 Doer | 按需 1~2 | 分工落地：各认领一块，按「单一变量 + 温和测试」执行 | 实际产出 + 验证证据 |

> 调查员与规划员、挑刺员可在**同一轮消息并行派 `delegate_task`**；执行员等 P 阶段定稿后再派。

## PDCA 四阶段（如何串起来）

### P — Plan（拆分 + 调查 + 规划 + 挑刺评审）
1. **拆任务**：把用户目标拆成可独立调查 / 执行的子块（用 `todo` 建卡）。
2. **派调查员**：每个陌生领域派 1 个子 agent 用 `web_search` / `web_extract` 联网搜索（遵守「先搜再判」红线），输出机制 + 坑位。涉及平台限流时，必须查清：错误码、限流时长、频率预算、升级规则。
3. **派规划员**：综合调查结果，产出明确方案，必须含：
   - **怎么做**（逐个串行 vs 多线程并发）——并基于调查结论论证取舍。
   - **处理多少条落盘验证**（定一个可证伪的验证阈值，如「先落 50 条验证链路通」）。
   - **间隔 / 频率**（遵守平台限流与频率预算）。
   - **灌库方式 + 幂等处理**（重复跑不产生脏数据）。
4. **派挑刺员**：审 plan，输出《漏洞清单》。**此步必须在正式 Do 之前完成。**
5. 主 agent 综合挑刺意见 → 修订 plan → 定稿，呈现给用户。

### D — Do（分工执行）
- 派 1~2 个执行员按定稿 plan 分工落地。执行员各自遵守：
  - **单一变量**改动，一次只验证一处。
  - **温和测试**（单次、低频、留间隔，**绝不连跑触发限流**）。
  - 遇陌生错误**先搜再判**，不猜 cookie / 不瞎改。

### C — Check（验证）
- 用**可证伪**的证据验证：落盘条数 > 阈值？灌库 `COUNT` 增长？接口返回符合预期？
- 验证失败 → 回到 P（但先查清原因，不盲目重试、不循环轰炸）。

### A — Act（改进 / 沉淀）
- 把本次机制 / 坑位 / 节奏写进对应 skill 或记忆，避免下次重蹈。
- 挑刺员发现的可持续改进点纳入下一轮。

## 具体执行模板（主 agent 如何一次性派活）

### 调查员 prompt 骨架（delegate_task）
```
你是调查员。任务背景：<用户目标>。
请用 web_search / web_extract 联网搜索<该领域>的官方文档与社区实测，重点查清：
① 平台/接口的风控与限流机制（错误码、时长、频率预算、升级规则）；
② 常见坑位清单（含版本差异、Windows/Linux 陷阱等）；
③ 官方推荐做法与反模式。
输出《领域机制与避坑清单》，每条结论附来源 URL。
不要写代码，只做调研。
```

### 规划员 prompt 骨架（delegate_task）
```
你是规划员。基于<调查员清单>设计执行方案。
必须明确：① 步骤拆分；② 技术选型与理由；
③ 节奏参数——并发还是串行、单次处理多少条、间隔多久；
④ 落盘验证阈值（可证伪）；⑤ 灌库方式与幂等处理；⑥ 回滚/失败处理。
输出《执行方案 v1》，要具体到可被挑刺员逐条审查。
```

### 挑刺员 prompt 骨架（delegate_task）
```
你是红队挑刺员。审<规划员的执行方案 v1>。
专找：① 未证伪的假设；② 是否忽略平台限流/风控（微信 freq control、HTTP 429、频率预算）；
③ 单点故障 / 幂等缺失；④ 验证标准能否证伪；⑤ 是否有更简路径。
输出《方案漏洞与改进建议》，逐条可改、可操作。不要执行，只审。
```

## 与既有纪律的关系（强制，违反即失职）
- **先搜再判**：调查员 / 执行员遇陌生错误必须 `web_search`，不猜 cookie、不瞎想当然。
- **跳过挑刺员 = 违反本工作法**：动手前必须有《方案漏洞与改进建议》这一环。
- **温和测试**：执行员单次低频，绝不为「验证修复」连跑触发限流；挑刺员须把「限流风险」列为首要审查项。
- **不折叠长输出**：PDCA 各阶段产出（清单 / 方案 / 漏洞）须完整呈现给用户，不压缩成结论式短句。

## 适用场景（不限于本项目）
所有项目、所有成规模任务通用思维骨架——微信爬取、云部署、数据库迁移、第三方 API 接入等任何「需要先摸清机制再动手」的任务，默认走本工作法。

## 反面教材（为何要有本 skill）
SLG 公众号采集翻车：撞微信 `ret=200013 freq control` 后**不搜风控规则**、反把根因一路归为 cookie（半成品 / pass_ticket / data_ticket 轮换假设），还**连跑 4 次**撞风控，直到被勒令才去查真实规则。
若当时走本工作法：调查员会先查清「200013 = 限流、频率预算、升级规则」，规划员据此定「单次串行 + 间隔 + 先落 50 条验证」，挑刺员会立刻指出「连跑会触发封禁」——根本不会连撞 3 次。

## Common Pitfalls
1. **省掉挑刺员**：图快直接 Do，结果 plan 有未证伪假设，执行到一半崩。→ 挑刺员是强制角色，P 阶段必须有《漏洞清单》才进 D。
2. **调查员不联网**：凭经验猜机制（尤其把一切归因 cookie）。→ 陌生领域必 `web_search`，每条结论附来源。
3. **连跑验证修复**：为"试试看修没修"高频重试触发平台限流（假性 429/503）。→ 单次、低频、留间隔。
4. **验证不可证伪**：只说"应该好了"，没落盘证据。→ 用条数 / COUNT / 接口返回做可证伪校验。
5. **脏数据回灌**：灌库无幂等，重跑覆盖干净数据。→ 灌库必须幂等，重复跑不产生脏数据。

## Verification Checklist
- [ ] 已用 `todo` 把目标拆成可独立调查 / 执行的子卡。
- [ ] 每个陌生领域派了 ≥1 个调查员子 agent，产出《领域机制与避坑清单》且每条附来源。
- [ ] 规划员产出《执行方案 v1》，含节奏参数 + 可证伪验证阈值 + 灌库幂等。
- [ ] 挑刺员产出《方案漏洞与改进建议》，且 P 阶段结束前已完成评审。
- [ ] Do 阶段执行员遵守单一变量 + 温和测试，未连跑触发限流。
- [ ] Check 阶段用落盘证据证伪（条数 / COUNT / 接口返回），失败则回 P 查清原因。
- [ ] Act 阶段把机制 / 坑位 / 节奏沉淀进 skill 或记忆。
- [ ] 各阶段产出已完整呈现给用户，无折叠。
