# 技术点 · 超大规模公开数据集的抓取、清洗与 Cloudflare Pages + D1 公网检索部署

> 对应项目轴 Handoff：`2026-08-02-handoff-skillhub-9-8-万技能市场调研与-cloudflare-部署上线.md`
> 目的：从该项目提炼**可复用技术资产**——怎么把一个 10 万级条目的公开社区数据集抓下来、怎么把超大 JSON 灌进 Cloudflare D1、怎么用 Pages + Functions 搭一个公网可检索的看板。下次做"公开数据集采集 + 轻量公网检索站"直接复用。

## 一、技术选型

| 选型项 | 选定 | 落选 | 依据 |
|---|---|---|---|
| 数据源 | **目标站官方 API（匿名可读、分页）** | 爬 HTML 页面 | 前后端分离应用，接口匿名可读、每页 20 条，比解析 HTML 稳且快（T1，已核实） |
| 采集并发 | **12 路并行后台采集（每分类一路）** | 单线程顺序 | 10 万级条目必须并行；错峰启动 + 退避重试避免触发风控（T1） |
| 导入通道 | **D1 REST API `{"batch":[...]}`** | 官方 CLI `d1 execute --file` | CLI 会把大文件整体当单条语句执行 → `SQLITE_TOOBIG`；REST 批交可控（T1，实测撞过坑） |
| 数据库 | **Cloudflare D1（APAC 区）** | 传统云数据库 | 与 Pages Functions 同生态、绑定即用、免费额度对 10 万行绰绰有余（实测已用约 97MB / 5GB，T1） |
| 前端形态 | **静态前端 + Functions API** | 全栈框架 | 只做检索不需要 SSR；静态页面零冷启动成本（Pages Function 冷启动偶发 522，重试即好，T1） |
| 本地预览 | **JSON 包装成 `window.SKILLS=[...]` 用 script 引入** | fetch 本地 JSON 文件 | 双击本地 HTML 直接打开时 fetch 本地文件会触发跨域限制；用 script 标签全局变量绕开，做到双击即用（T1） |
| 检索能力 | **后端 Functions 做分页/分类/搜索/排序** | 前端一次性全量过滤 | 10 万条放前端全量过滤会卡；后端按需返回（T1） |

## 二、实施要点与关键技术

### 采集

1. **判定 API 是否匿名可读是第一道关**。先发单请求确认返回的是真实 JSON 而非登录页/挑战页，再上并发。错过这步会把挑战页当数据读进来（T1）。
2. **12 路并行要错峰 + 退避**：各分类一路启动时间错开，撞错按指数退避重试；配合断点续传，中途断网可从断点续跑，不重头（T1）。
3. **去重是硬指标**：98,824 个条目是去重后的结果，采集时就要按稳定主键去重，否则分页重叠会产生大量重复（T1）。

### 灌库（最关键的两坑）

4. **`d1 execute --file` 大文件陷阱**：CLI 把整个 .sql 当一条语句发给 SQLite，超过单条上限就 `SQLITE_TOOBIG`。10 万行数据绝不能这样导（T1，实测撞过）。
   **正解**：用 **D1 REST API** 的 `{"batch":[...]}` 分批提交，每批控制行数。
5. **D1 单条 SQL 硬上限 = 100,000 字节**。按字节切分，**单条 < 80KB** 留安全余量（T1）。
   ```text
   实测：skillhub_all.json 154MB → 按字节切分 → 分批 batch 提交 → 全部落库
   ```
6. **幂等 + 断点续传**：用 `INSERT OR IGNORE` 保证重复执行不产生重复行；用 `import.ckpt` 记录进度，中断后可续传（T1）。

### 部署

7. **`wrangler.toml` 关键配置**：
   ```toml
   pages_build_output_dir = "public"
   [[d1_databases]]
   binding = "DB"   # 前端/函数里用 env.DB 访问
   ```
   D1 在 APAC 区创建，绑定名 `DB`（T1，本项目实测）。
8. **Functions 路由**：`functions/api/skills.js`（分页/分类/搜索/排序）+ `functions/api/stats.js`（total / 分类计数 / 已验证数）。函数里通过 `env.DB` 拿绑定实例（T1）。
9. **首访冷启动 522**：Pages Function 偶发冷启动超时，重试一次即 200，属正常非故障（T1，curl 实测全 200）。
10. **前端用 `window.SKILLS` 全局变量**：把精简版数据 `skillhub_min.js`（`window.SKILLS`）用 `<script>` 引入，绕开本地文件跨域，双击即用（T1）。
11. **schema 预留扩展**：设计时就留好全文检索（FTS5）字段与"推荐/对比/收藏/提交"所需列，后续迭代不必改表结构（T1）。

## 三、模块职责划分

- **采集层**：只负责"按接口分页拉取 + 去重 + 断点续传"，产出原始 JSON。
- **清洗/调研层**：在原始 JSON 上做分类维度统计、头部筛选、商业切口分析，产出调研文档，不改原始数据。
- **存储层（D1）**：只负责持久化结构化数据，对外通过 Functions 暴露查询能力。
- **接口层（Functions）**：只负责把请求翻译成 SQL 查询并返回 JSON，不含业务逻辑。
- **展示层（静态前端）**：只负责把 API 返回的 JSON 渲染成可检索界面。
- **合规层（横切）**：贯穿采集与展示，约束"索引/评论/推荐/跳转"边界，禁止转售/搬运他人文件。

## 四、如何选型（可复用的决策方法论）

- **公开数据集要不要抓**：先看它是不是"用户创作、免费下载"的社区站。若是，抓取 + 做索引/评论/推荐 + 跳转链接通常合规，但**转售或搬运原文件**侵犯创作者权益且违反 ToS（T1，本项目明确合规边界）。
- **10 万级数据怎么落库**：关系型 + 需要公网 + 免费 → D1 是强候选；但必须放弃 CLI 整文件导入，走 REST 分批 + 按字节切分。
- **冷启动 vs 简单性**：无状态的静态前端 + Functions 最省事，但要接受"首访偶发 522 重试"；若不能容忍，考虑常驻后端（成本上升）。
- **本地预览跨域**：交付可双击打开的 HTML 看板时，避免 fetch 本地文件，改用全局变量注入或起一个本地静态服务器。
- **调研 vs 搬运**：调研报告可以引用官网 `description`（属"介绍/索引"范畴），不要把原 skill 文件再分发——这是合规与侵权之间的硬线。

## 六、技术结合点

- **REST 分批 + 字节切分 + 幂等**：三者必须同时成立才灌得进 10 万行。只分批不切字节会撞单条上限；只切字节不幂等，中断续传会插重复行。
- **静态前端 + Functions + D1 绑定**：前端负责轻交互，Functions 负责把查询转成 SQL，D1 绑定让函数无需管连接串。整套零运维、免费、公网可达。
- **全局变量注入 + 本地双击**：把数据塞进 `window.SKILLS` 而非 fetch，让调研看板不依赖本地服务器就能用，极大降低"给别人看"的门槛。
- **采集去重 + 灌库幂等**：上游采集就去重，下游灌库再幂等，两层防护保证最终 D1 里的 98,824 行既无遗漏也无重复——这是"数据量看起来对"能成立的前提。
- **合规边界 + 公网开放**：站定位为"免费流量入口"而非营收源，决定了它只做索引/跳转。合规约束反向简化了架构——不用做用户系统、不用做交易，Functions 只需只读查询。
