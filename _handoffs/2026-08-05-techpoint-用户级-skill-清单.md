# 技术点 · 用户级 Skill 资产清单的自动化盘点

> 对应项目轴 Handoff：`2026-08-05-handoff-用户级-skill-清单.md`
> 目的：从该项目提炼**可复用技术资产**——「如何把一堆分散、多层嵌套、带状态的 skill 目录，盘点成一张可复用的能力资产表」的方法与字段口径。下次要清点任何 `.workbuddy` / 插件 / 扩展资产时直接套用。

## 一、技术选型

| 选型项 | 选定 | 落选 | 依据 |
|---|---|---|---|
| 盘点对象 | **用户级 `~/.workbuddy/skills`** | 内置/连接器的 skill | 用户级才是本机真正可调用的资产全集，内置的是环境自带的（T1） |
| 扫描方式 | **递归扫描含子命名空间与嵌套子技能** | 只扫一层目录 | `@kekewater/china-stock-data`、`cangjie-skill/books/.../fw01` 这类嵌套要让能力出现在正确位置；本项目扫描到 39 个 SKILL.md（T1 实测） |
| 字段来源 | **`description` 优先，缺失回落 `summary`** | 只取其一 | 不同作者填的字段不同，固定一个会漏掉说明；本项目用两级回落保证每行都有说明（T1） |
| 状态字段 | **`disable:true` + `agent_created`** 两个标记 | 仅看目录名 | 目录名看不出是否禁用或是否 AI 自建；这两个标记才是真实状态（T1） |
| 落点形式 | **Markdown 表格（带序号/目录/名称/说明/状态）** | JSON / 数据库 | 表格易读、易 grep、易后续做差异对比（T1） |

## 二、实施要点与关键技术

1. **用 Glob 扫描，别用 `find` 拼中文名**（T1，当天实测踩过的坑）：Git Bash 下 `find . -name "*_每日工作总结.md"` 因 locale 问题返回空集，会误判"文件不存在"。**结论：查中文文件名一律用 Glob，不要单用 `find`。**

2. **递归深度要覆盖多层命名空间**：本项目目录树形如
   ```
   @kekewater/china-stock-data/SKILL.md
   cangjie-skill/books/caifuziyouzhilu/fw01-wealth-freedom-definition/SKILL.md
   agent-plan-router/SKILL.md
   ```
   扫描器必须能落在任意深度找到 `SKILL.md`，并保留从顶层到该文件的完整路径（这是"目录"列的值）。

3. **说明字段的两级回落**（T1）：
   - 优先取 frontmatter 的 `description`
   - 缺失时取 `summary`
   - 都没有则留空并在状态列标记（本项目里部分 `fw01` 类子技能 `description` 为空、靠 `summary` 补）

4. **状态必须读元数据，不能看目录名**（T1）：本项目有 4 种典型状态——
   - 启用
   - 已禁用（`disable:true`）
   - AI 自建（`agent_created`）
   - 已禁用 / AI自建（两者叠加）

   其中很多条目**目录名完全一致、只是状态不同**（如 `fw01-wealth-freedom-definition` 在 `cangjie-skill/books/...` 下是"已禁用"，在顶层是"启用"）。**不读元数据就会把两条当成一条，或漏掉"同名但不同状态"的真实分布。**

5. **多行 YAML 字段的处理**（T1）：部分 `description` 是多行英文（如 `agnes-media-gen` / `impeccable` / `cangjie-skill`）。盘进表格时**逐行保留换行**、不要压成一行，否则表格列会错乱。

6. **去重的口径**：同名 skill 出现在不同路径且状态不同，应**分别列出**而非合并——它们代表不同的启用上下文（顶层全局启用 vs 嵌套在 cangjie 书库下被禁用）。

7. **（关联）盘点之外的两个关键约束**（来自当日日志，属同一条 skill 资产主线）：
   - **创建 skill / 注册计划任务属高危操作**，必须先 `AskUserQuestion` 弹框确认，不能自作主张（当天限流雷达就因"只说模仿、实际自作主张做成 skill + 挂计划任务"被红牌）。
   - **skill vs 独立项目的判定**：长周期、有常驻进程（daemon/看门狗/计划任务）的，应是独立项目目录（`D:\AI work\workbuddy\...`），不是塞进 `~/.workbuddy/skills` 的 skill；skill 适合"触发即跑、跑完即退"的原子能力。

8. **（关联）多宿主的 skill 复用差异**（T1）：同一份能力在 WorkBuddy 与 Hermes 的落盘路径不同（`~/.workbuddy/skills` vs `~/.hermes/skills/<category>/<name>/`），但**落盘即生效、不需改索引**是两者共性；工具名映射（Agent→delegate_task 等）是 Hermes 侧额外要做的。盘 UserBuddy 资产时不必管映射，但要知道跨宿主搬运时要改工具名。

## 三、模块职责划分

- **扫描器 = 发现层**：只负责把全部 `SKILL.md` 找出来，不解释、不评判。
- **字段抽取 = 解析层**：从每个 frontmatter 取名称/说明/状态，按既定优先级回落。
- **资产表 = 呈现层**：把分散的目录结构压成一张带序号的表，供人快速浏览与做差异对比。
- **状态标记 = 决策辅助层**：`disable` / `agent_created` 是后续"要不要启用/清理/重写"的输入。
- **（跨宿主）映射层**：仅在不同宿主间搬运时存在，负责把工具名/路径对齐目标宿主约定。

## 四、如何选型（可复用的决策方法论）

1. **盘点前先定"资产边界"**：是只数用户级，还是连内置一起？边界不清盘点结果就不可比。本项目明确只数用户级，结论才干净。
2. **字段优先级要写死**：`description` → `summary` → 空标记，不要每次临时决定，否则两次盘点口径不一致、差异无从谈起。
3. **状态必须来自元数据而非路径**：这是盘点最容易错的坑。同名不同状态、同名不同路径，真实分布只有读了 frontmatter 才知道。
4. **"发现"与"处置"分离**：盘点只负责呈现，不要在盘点报告里顺手启用/删除/改写。处置是另一类操作，且删除/改写属高危、需授权（见技术结合点）。
5. **把 skill 资产当成"可删可改"看待，不是"只读目录"**：因为同一条主线证明，第三方 skill 里可能藏着硬编码 token 与非官方重定向（见另两篇 techpoint）。清单的价值之一是**标出"哪些需要优先审计"**。
6. **判断一个东西该是 skill 还是独立项目**：有常驻进程/计划任务/守护进程 → 独立项目；触发即跑 → skill。错配会导致流程越界（当天红牌直接来自这条）。

## 六、技术结合点

- **递归扫描 + 状态标记**：单有递归会找到文件但不知道哪个能用；单有状态标记却扫不全嵌套子技能。**两者合起来才是"完整且带可用性"的资产视图**——尤其当同名 skill 在全局启用、在书库下禁用时，缺任一个都会失真。
- **字段优先级回落 + 表格呈现**：回落保证每行都有说明不空缺，表格保证 39 条能被一眼扫完。任一缺失都会让清单出现空行或漏说明，复用价值下降。
- **Glob + 中文路径**：在中文 Windows 的 Git Bash 下，这对组合是"能查到"和"误判不存在"的分水岭。前者踩过坑（find 返回空集导致重复生成/重复发布），后者是当天固化下来的正确做法。
- **盘点报告 + 审计/处置红线**：清单负责"把家底亮出来"，红线负责"看见硬编码 token / 想清理时不越权"。只盘点不动手是空转，盘点完直接改是越界；**清单给出范围、授权决定动作**，这个分工让"摸清资产"和"安全处置"各归其位。
- **skill 口径 + 独立项目口径**：同一份能力盘点时按 skill 算，但落地形态要按"是否常驻"判断是否该独立成项目。这个结合点防止了"凡是能力都塞 skill"的惯性，也直接规避了当天那张红牌。
