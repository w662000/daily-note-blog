# 技术点 · Hermes 接入模型评分表（纯 5 站榜单视角 · MoA 选型）

> 对应项目轴 Handoff：`2026-08-08-handoff-hermes-接入模型评分表-纯-5-站榜单视角-moa-选型.md`
> 目的：抽出「给一批已接入模型做多榜单评分、为 MoA 选主力/助手」这条链路里的**可复用技术资产**——异质量纲归一化方法、可信度标注纪律、实测缓存作数据源、以及「改前查证 / 版本化备份 / 工具故障绕行」的工程习惯。下次做模型选型表可直接复用。

## 一、技术选型

| 选型项 | 选定 | 落选 | 依据 |
|---|---|---|---|
| 评分数据来源 | **本机实测缓存 `provider_models_cache.json`（75 条 → 去重 64 个）** | 网上榜单截图 / 拍脑袋 | 这是本机真实接入记录，T0 可信；避免引用过期或口径不明的榜单（T0） |
| 榜单集合 | **5 站：LMArena / Artificial Analysis / LiveBench / Chatbot Arena / SuperCLUE** | 单站或自编加权 | 单站偏差大；用户指定 5 站；Chatbot Arena 已于 2024 更名 LMArena 同源，表中并列但介意可只看 LMArena（T1） |
| 综合分算法 | **5 站各自归一化到 0–100 后取算术平均（不去重）** | 能力×0.55+速度×0.15+成本×0.15+中文×0.15 加权 | 用户要求「直接按 5 站评分评」，加权版口径差异大且会把 hy3 排到非真实位置（T1 用户返工） |
| 量纲处理 | **Elo 分与百分制按真实量纲分别展示，综合前再归一化** | 强行统一量纲 | LMArena/AA/Chatbot Arena 用 Elo（~1150–1500），LiveBench/SuperCLUE 用百分制（0–100），混算会失真（T1） |
| 未来型号处理 | **标 N/A 排表末，不编造分数** | 用代际估算填分 | 44 个 2026 预置型号公开榜单查无数据，编分会污染选型结论（T1 红线） |
| 生成方式 | **`model_score_build.py` 跑数 + 同路径覆盖更新 md/html** | 手工填表 | 口径一改就要重算，脚本化保证可复跑（T1） |

## 二、实施要点与关键技术

1. **同源重复要显式声明**：Chatbot Arena 2024 已更名 LMArena，两列同源。表内忠实并列，但注明「介意重复计权可只看 LMArena」，避免读者误以为信息量翻倍（T1）。
2. **未来型号一律标 N/A**：沙箱预置的 gpt-5.6 / claude-opus-4.8 / gemini-3.x / deepseek-v4 等在真实公开榜单无数据，5 站全标 N/A、综合 N/A、排表末。**不瞎编数字**——这是选型表可信度的生命线（T1）。
3. **改算法前先确认口径，避免返工**：第一版用四维加权（hy3 排第一 81.1），用户要求改纯 5 站后主力只剩 3 个（claude-sonnet-5 90.3 / claude-sonnet-4 85.1 / gemini-2.5-pro 82.4）。**两版结论差异很大，引用时必须说清是哪版**，否则 MoA 配置会建在错的基础上（T1）。
4. **改前联网查证，不猜「接口挂了」**：同批看板个股查不出数，先查 akshare 源码 + ExcelHome 实测 + 教程三方交叉，定位出真因是 URL 少了必选参数 `ut=b2884a393a59ad64002292a3e90d46a5`（东财 `push2his` 系必带）。若凭经验猜「被风控」会白折腾一晚（T1 红线实践）。
5. **大改前做版本化备份**：单文件 HTML（5 万字节级）每次大改前 `cp` 出 `v1.0`/`v1.2` 副本，回滚点齐全。改这类无版本控制的大文件必须保留历史快照（T1）。
6. **长耗时/工具故障用子进程绕行**：会话内 Bash/PowerShell 持续报工具层 bug（`command expected string`）时，派 `Agent(general-purpose)` 子进程去执行 Python 脚本与全盘搜索，是已验证有效的绕行方案（T1）。
7. **评分表只是起点，落地才是系统**：表做完后主力/助手分工一行都没写进 Hermes 的 `config.yaml`，MoA 模式零次真跑——这是「囤了工具没跑系统」的典型。选型表必须配「落地动作」才算闭环（T1）。

## 三、模块职责划分

- **数据源层（`provider_models_cache.json`）**：本机真实接入记录，模型清单的唯一权威来源；任何选型都从这里取名单，不从记忆里补。
- **归一化层（`model_score_build.py`）**：负责把 Elo 与百分制分别映射到 0–100，再算术平均。量纲处理集中在此，换口径只改这里。
- **榜单层（5 站原始分）**：各站按其真实量纲展示，只呈现不加工；加工交给归一化层。
- **结论层（MoA 角色标注）**：主力（综合≥80 且现实存在 + 代际 S/A）/ 助手（快/省、适合 fan-out 与校验），标注需同时看「综合分」与「是否存在真实榜单数据」两列。
- **可信度标记层**：每个模型挂 T0/T1/T2 与「免费期限」等时效注记，使选型可复核。

## 四、如何选型（可复用的决策方法论）

- **有真实数据才给分，无数据就标 N/A**。选型表的权威来自「每条分数都能追到榜单」，未来型号无数据宁可排表末也别编——编一个就毁掉整张表。
- **异质量纲先分列后归一**。Elo 与百分制千万不能混算，先按真实量纲展示、综合前再各自归一，否则高量纲轴会主导结果。
- **加权口径要和用户意图对齐**。用户要「纯榜单」就别加速度/成本/中文权重；需要综合体验再单独做加权版，但两版并存时必须标注清楚，避免混用。
- **数据源用实测缓存而非二手截图**：本机 `provider_models_cache.json` 是已接入事实，比网图可靠，且可复算。
- **选型表不是终点**：评分 → 落 `config.yaml` → 真跑一次 MoA，才算把「表」变成「在跑的系统」。

## 六、技术结合点

- **实测缓存 + 归一化层**：实测缓存保证「名单真实」，归一化层保证「量纲可比」，二者结合才产出可采信的 5 站综合分。缺前者会混入未接入模型，缺后者会让 Elo 轴碾压百分制轴。
- **量纲分列 + 综合前归一化**：先把不同量纲如实呈现（可审计），再在综合步骤统一，避免「为了好看强行统一」丢失信息。
- **T 级标注 + 未来型号 N/A**：可信度标记与 N/A 处理是同一纪律的两面——已知不确定的标低可信度，完全无数据的标 N/A，共同维护选型表不被污染。
- **改前查证 + 版本化备份**：联网查证避免把「参数缺失」误判成「接口挂了」；版本化备份让大改可回滚。两者都是「在大文件/长链路改造中不翻车」的护栏。
- **评分表 + 落地动作**：评分表提供决策输入，落到 `config.yaml` 并真跑 MoA 才形成闭环。只做表不做落地，资产就停在「纸面」。
