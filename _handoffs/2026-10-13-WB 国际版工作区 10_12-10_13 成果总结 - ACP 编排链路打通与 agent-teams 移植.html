10/13 · 真实缺陷：评审解析器把小节标题当成 must-fix
垃圾标签被原样喂回下一轮产出方，属于会持续污染流水线的 bug
现象：mustFix: ["1) VERDICT: pass", "2) BLOCKERS: None (0).", …]， score 抓到 1（来自 "1) VERDICT" 里的 1）。
修法：lib/judge.mjs 新增 parseExternalReview() 按 5 个分节切片：mustFix = BLOCKERS 区 - 条目 + SUGGESTED PATCH 区 + 行； score 只认显式 5) SCORE: n/10，没有就 null，不伪造。 固化回归测试 tests/parse-external-review.test.mjs（19 断言，含真实评审文本 fixture）。
10/13 · 宿主 hook 注入故障被误当成产物
且被真实复现过
某一轮 codebuddy 的"产物"其实是 UserPromptSubmit operation blocked by hook … subscription-gate/dist/gate.mjs … Hook timed out after 10000ms。
修法：isHostHookError() 要求两个短语同时出现才判定（避免误判"介绍 hook 的文档"）， 命中则换新 session 重试 1 次。CLI 查过没有 --no-hooks 开关，只能重试。

四、关键突破：认证链路的因果链

1
现象：stopReason=refusal + Authentication required. Please use /login，产物 0 字节。
2
排除：模型解析正常（ModelConfig resolved model=deepseek-v4.1-flash）、 遥测正常发出 → 请求打到网关被 401。
3
排除：环境变量传递无效（补 CODEBUDDY_CONFIG_DIR / 继承完整宿主 env，三种策略全 refusal）。
4
真因：token 存于 at-rest 加密文件，解密密钥只给桌面端自己 spawn 的子进程；我们 spawn 的 CLI 角色是 cbc → 读不出 token → 401。
5
加剧：两个 ProductProvider 并行竞态 → 同一命令 3 次跑出 fail/success/fail。
6
解法：走最高优先级 env 认证源 CODEBUDDY_AUTH_TOKEN，值从明文兄弟文件读取 → 绕过文件解析、消灭竞态。

六、方法论沉淀（比代码更值钱的部分）

教训说明
判据必须钉死stopReason=end_turn 不等于模型真被调用了——hook 拦截也会给 end_turn。验证时必须同时确认产物内容。本次因这条误判了两次。
不要为「清环境」strip 代理沙箱/宿主的网络出口代理很可能同时承担凭据注入。
排查模型调用失败的第一顺位看 CLI 日志的 stopReason + refusal classified category，一眼区分 auth / empty_model_response / 上游故障，比客户端侧猜快得多。
不要用「改 product id」绕竞态CLI 有两个 ProductProvider 并行，任何 id 覆盖都不稳。用最高优先级 env 认证源才是确定性的。
长产物评审必须调大 maxArtifactChars否则 judge 只看到前半篇却照样给出 PASS。
judge PASS ≠ 无缺陷judge 只按 rubric 打分，rubric 没覆盖的维度（Schema 自洽性、CLI 参数真实性）它不会主动查。编排者通读不可省——本次 6 项实质缺陷全是人读出来的。
修订轮要「逐条 + 修复要求 + 若不同意请说明理由」比笼统说"再改改"有效得多。
账户 uid 即使在加密认证文件里也是明文是做账号锚点的好材料。
CODEBUDDY_CREDENTIALS_IN_MEMORY=1 会禁用会让 CLI 既读不到也写不了 auth 文件（每次 hasSession=false）。
