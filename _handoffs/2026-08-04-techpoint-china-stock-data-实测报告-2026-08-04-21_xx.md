# 技术点 · 上游接口漂移修复与凭据有效性温和探测

> 对应项目轴 Handoff：`2026-08-04-handoff-china-stock-data-实测报告-2026-08-04-21_xx.md`
> 目的：从该项目提炼**可复用技术资产**——「第三方封装库上游改名怎么最小成本修」「一个来路不明的 token 怎么在不触发限流的前提下判定它死活」「发现供应链风险后怎么处置」。这三件事在任何依赖外部数据源的项目里都会反复遇到。

## 一、技术选型

| 选型项 | 选定 | 落选 | 依据 |
|---|---|---|---|
| 依赖版本策略 | **升到最新版**（akshare 1.18.81 / tushare 1.4.29） | 锁旧版规避改名 | akshare 上游接口本身在变，锁旧版只是把问题推后；且旧版可能已无人维护对应的东财接口（T1） |
| 接口漂移修法 | **最小改动：换函数名 + 同步列名** | 重写整个数据获取函数 | 参数签名 `symbol=` 未变，改动面越小越好验证（T1 实测有效） |
| 研报数据源 | **`ak.stock_research_report_em`**（东财研报） | 已被移除的 `ak.stock_jsyjs_anal_em` | 前者是新版对应接口，返回列更全（含 PDF 直链 + 盈利预测）（T1） |
| token 探测方式 | **单次调用 + 间隔 3s + 逐接口试探** | 批量并发探测 / 重试循环 | 目标是判定有效性，不是压测；并发探测会触发限流，反而污染结论（T1，全程未触发限流） |
| 探测 endpoint | **先官方 `api.tushare.pro`，再复现 skill 实际路径** | 只测 skill 实际路径 | 分离变量：先确认 token 本身死活，再确认代理层行为，两者结论互相印证（T1） |
| 凭据存放 | **环境变量 `TUSHARE_TOKEN`** | 硬编码 / 配置文件 | 与该项目其它 7 个数据源保持一致；不随代码分发（T1） |

## 二、实施要点与关键技术

### A. 上游接口漂移的定位与修复

1. **症状识别**：`module 'akshare' has no attribute 'stock_jsyjs_anal_em'`。
   `AttributeError` 指向模块属性缺失，**不是网络问题也不是参数问题**——第一反应就应该是上游改名或移除，不要去查网络。

2. **修复动作（最小改动原则）**：
   - 函数名：`stock_jsyjs_anal_em` → `stock_research_report_em`（参数签名 `symbol=` 不变）
   - **列名必须同步更新**，这是最容易漏的一步。新版返回列：
     `股票代码 / 股票简称 / 报告名称 / 东财评级 / 机构 / 行业 / 日期 / 报告PDF链接 / 2026-盈利预测-收益 / 2026-盈利预测-市盈率`
   - 改动落点：`scripts/china_stock.py` 的 `akshare_report()`

3. **验证要用真实数据，不能只看"不报错"**（T1）：
   ```bash
   $PY $SCRIPT report 600519 5   # 返回 5 条真实研报，含机构/评级/PDF 直链/盈利预测
   $PY $SCRIPT report 000001 3   # 返回 3 条（国信/东兴证券）
   ```
   两只不同板块的票各跑一次，确认不是偶然。

4. **通用结论**：**封装类库（akshare 这类）会频繁重命名接口**，把它当"稳定 API"是错的。依赖它的代码要有心理准备：函数名会变、列名会变，参数签名反而相对稳定。

### B. 凭据有效性的温和探测

5. **探测协议（可直接复用）**：单次调用、间隔 3s、逐接口试探、失败不重试。**目的是判定，不是压测**。本项目全程未触发任何限流。

6. **分两层探测，把变量拆开**：

   **探测 1 — 走官方 `api.tushare.pro`**（安全，不碰第三方域名）
   对 6 个接口逐一试：`stock_basic / daily / trade_cal / anns_d / fina_indicator / income`
   结果：**全部返回"您的token不对，请确认"** → token 在官方端完全无效，0 个接口可用。

   **探测 2 — 复现 skill 实际路径**（重定向到 `tushare.xyz`）
   只调 skill 里 `tushare_announce` 实际用的 `anns_d` 一次
   结果：**`[.xyz异常] Token已过期，请续费重新激活`** → 在代理端也已过期。

   | 目标 endpoint | 返回 | token 状态 | 可调数据 |
   |---|---|---|---|
   | `api.tushare.pro`（官方） | 您的token不对，请确认 | 无效 | 0 个接口 |
   | `tushare.xyz`（skill 重定向） | Token已过期，请续费重新激活 | 过期 | 0 个接口 |

   **两端结论一致 → 判定成立**：该 token 已死，`tushare-ann` 及任何 Tushare 依赖路径当前实际不可用。

7. **"最少接口 + 最少次数"原则**：探测 2 只调一个接口一次。因为探测 1 已经给出结论，探测 2 只需要交叉验证代理层行为，不需要再跑 6 个。

### C. 🔴 供应链风险的识别与处置

8. **两个独立问题，不要混为一谈**（`china_stock.py` 第 511–512 行）：
   ```python
   client.DataApi._DataApi__http_url = "http://tushare.xyz"   # 静默改指向非官方域名
   TUSHARE_PRO = ts.pro_api('c8dbb...')                       # 硬编码 token
   ```
   - **第 512 行 = 凭据管理问题**：明文写死随包分发，谁装谁拿得到。
   - **第 511 行 = 供应链问题，且更严重**：把请求静默改发到非官方域名。**即使 token 有效，数据也经过不可信第三方代理，来源与完整性无法验证。**
   注意它用的是 Python 私有属性名改写（`_DataApi__http_url`），这种写法本身就意在绕开正常配置入口——**看到私有属性被外部改写，优先怀疑是刻意规避**。

9. **修复方案（三步，需用户授权后执行）**：
   - 删第 512 行硬编码，改 `TUSHARE_PRO = ts.pro_api(os.environ.get('TUSHARE_TOKEN'))`
   - 删/改回第 511 行，恢复官方 endpoint
   - 未设 token 时**优雅降级**（该源标记不可用），不要直接抛异常中断整个 CLI

10. **修复后的验证点**（T1，当日已执行）：确认默认 endpoint 恢复为官方 `api.waditu.com`；确认未设 `TUSHARE_TOKEN` 时优雅降级；并把"如何获取 `TUSHARE_TOKEN`"的完整步骤写进 SKILL.md——**修完要留使用说明，否则用户只知道坏了不知道怎么修好。**

11. **红线**：修改安装产物属"重写"类操作，本项目是先出报告 + 给出 A/B/C 三个选项（A 应用修复 / B 只用自己 token 验证 / C 只出结论不动脚本），**拿到用户明确授权后才执行**。

## 三、模块职责划分

- **探测脚本 = 只读判定层**：单次调用、不写任何配置、不修改被测对象。职责是"给出事实"，不做处置。
- **报告 = 决策输入层**：把探测结果、风险等级、可选处置方案摆出来，**不替用户做决定**。
- **修复动作 = 变更层**：只在拿到授权后执行，且改动限定在已识别的具体行号。
- **凭据来源 = 环境变量层**：与代码彻底分离，保证代码可公开分发。
- **降级逻辑 = 容错层**：凭据缺失时该源不可用，但不影响其它 7 个源——这是多源架构在凭据层的兑现。

## 四、如何选型（可复用的决策方法论）

1. **`AttributeError` 类错误优先怀疑上游改名**，不要先查网络/参数。修法首选"改名 + 同步字段"，不要顺手重写整个函数——改动面越小，验证越容易，回滚越干净。
2. **判定凭据死活，用"分层探测"而不是"一把梭"**：先测官方端点确认 token 本身，再测实际调用路径确认中间层。两个结论互相印证才可信；只测一层，无法区分"token 坏了"和"代理坏了"。
3. **温和探测的三条硬约束**：单次、有间隔（3s 起）、失败不重试。**触发限流会污染结论**——你分不清返回错误是因为 token 无效还是因为被限流了。
4. **凭据管理的判据是"能不能公开这份代码"**：能，说明凭据分离做对了；不能，说明有东西不该在里面。
5. **供应链风险比凭据泄漏优先级更高**：token 泄漏影响的是一个账号，请求被静默改发第三方影响的是**所有数据的可信度**。发现后者要立刻停止依赖该路径的所有结论。
6. **修改他人产物前必须给选项**：至少给"改 / 只验证不改 / 只出结论"三档，让用户在知情前提下选风险承受度。

## 六、技术结合点

- **分层探测 + 温和协议**：分层保证结论可归因（token 问题还是代理问题），温和保证结论不被限流污染。两者缺一，探测结果都不可用——并发探测出来的错误，你无法证明是 token 无效导致的。
- **最小改动修复 + 真实数据验证**：改动小所以能快速定位问题，真实数据验证才能证明列名也对上了。只做前者会得到"不报错但字段全空"的假成功。
- **环境变量凭据 + 优雅降级**：凭据外置后必然有"没配"的状态，如果不做降级就会让整个 CLI 在启动时崩溃。两者必须成对实现。
- **报告分级（凭据问题 / 供应链问题）+ 处置分级**：凭据失效只是能力缺失，可以慢慢修；请求被改发第三方是信任问题，要立刻停用。把两类问题分开描述，用户才能正确排优先级。
- **接口漂移修复 + `references/` 知识沉淀**：这次改名的映射关系（`stock_jsyjs_anal_em` → `stock_research_report_em` + 新列名）本身就是资产。写进参考笔记，下次同类报错能秒查。
- **授权红线 + 完整选项**：红线保证不越界，选项保证不空转。只有红线会导致"发现问题却什么都没推进"，只有行动会导致越权——两者结合才是既安全又有产出的处置方式。
