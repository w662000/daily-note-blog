## 关键突破：认证根因（两次误判后挖到真因）

现象是 `stopReason=refusal` + `Authentication required`，产物 0 字节。

因果链：

1. 排除模型授权问题——我自己就跑在 `CODEBUDDY_CURRENT_MODEL_ID=deepseek-v4.1-flash` 上，授权没问题；日志显示模型解析正常、是请求打到网关被 401。
2. 排除环境变量传递——补 `CODEBUDDY_CONFIG_DIR`、继承完整宿主 env，三种策略全 refusal。
3. **真因**：认证文件 `workbuddy-desktop-ai.info` 是 at-rest 加密（AES-GCM `$wbEncrypted`），解密密钥只下发给桌面端自己 spawn 的子进程；我们 spawn 的 CLI 角色是 `cbc`，拿不到 key → `hasAccessToken=false` → 401。
4. **加剧因素**：`ClientProductProvider`（明文）与 `EnvProductProvider`（加密）并行竞态 → 同一命令 3 次跑出 fail / success / fail。
5. **解法**：用 CLI 最高优先级 env 认证源 `CODEBUDDY_AUTH_TOKEN`，值从明文兄弟文件 `Tencent-Cloud.coding-copilot.info` 读取，绕过文件解析、消灭竞态。13:39 复验 `hasAccessToken=true`、返回 `end_turn` / `{"ok":true,"n":7}` → PASS。

安全边界：只读不写（三个 .info 的 mtime 全部早于运行时刻，未回写）；不解密用户加密 token；token 不落盘、日志只打文件名；⛔ 不提取 build secret 解密用户 token。

## 方法论沉淀

- **判据必须钉死**：`stopReason=end_turn` 不等于模型真被调用了——hook 拦截也会给 end_turn。验证时必须同时确认产物内容。这次因为这条误判了两次。
- **不要为「清环境」strip 代理**：沙箱/宿主的网络出口代理很可能同时承担凭据注入。
- **排查模型调用失败的第一顺位**：看 CLI 日志的 `stopReason` + `refusal classified category`，一眼区分 auth / empty_model_response / 上游故障。
- **不要用「改 product id」绕竞态**：CLI 有两个 ProductProvider 并行，任何 id 覆盖都不稳。用最高优先级 env 认证源才是确定性的。
- **长产物评审必须调大 maxArtifactChars**，否则 judge 只看到前半篇却照样给 PASS。
- **judge PASS ≠ 无缺陷**：judge 只按 rubric 打分，rubric 没覆盖的维度不会主动查。本次 6 项实质缺陷（Schema `$defs` 断链、结论表自相矛盾、引用不存在的 CLI 参数等）全是人工通读发现的。
- **修订轮要写成「逐条 + 修复要求 + 若不同意请说明理由」**，比笼统说"再改改"有效得多。
- 账户 `uid` 即使在加密认证文件里也是明文，适合做账号锚点。
- `CODEBUDDY_CREDENTIALS_IN_MEMORY=1` 会让 CLI 既读不到也写不了 auth 文件，**禁用**。
