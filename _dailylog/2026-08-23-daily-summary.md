## 二、关键决策 / 注意事项

- **这次的根因和 08-21 完全不同，别搞混。** 08-21 是 WorkBuddy 后端 **429 限流**（配额用满，等次日 09:52 重置）；08-23 是**本地代理进程没启动**导致 502 拒连。前者是"服务端不让用"，后者是"本机自己没通网"。两者表现都是"自动化全线失败"，但处置方式截然不同：限流只能等，代理断了必须手动起进程。
- **同一天其实是"三重故障"叠加，排查时务必分开看：** ①本机代理断（502，掐掉所有 WorkBuddy 模型调用）；②云端语雀 API 429（掐掉语雀发布，与①完全无关，即使本机正常也发不出去）；③前一天 08-22 的编排器卡死已埋下缺口。三者互相独立，只修一个不解决问题。
- **发现一个设计缺陷：存在性检查失败时的降级策略是错的。** 语雀脚本在"拉取文档列表"失败时打印"将直接尝试发布（同名会报错可忽略，不影响幂等）"，然后全量重发。但在**限流场景**下这个降级恰恰是最坏选择——列表接口 429 说明写接口更会 429，此时全量重发只会把限流打得更死、并把 run 拖成 4.5 小时。更合理的做法是：列表拉取失败即**直接放弃本轮**，等下一次调度。
- **最大的教训：整个自动化体系强依赖一个本地代理进程，且这个依赖是单点、无守护、无告警的。** 代理一挂，20 个任务静默全灭，跑一整天都不会有人知道。这是继 08-22 编排器卡死之后，**连续第二天**因为基础设施问题损失全天产出。
- **失败很"快"反而更危险。** 每个任务 20~35 秒就失败退出，看起来"跑过了"，日志不翻到 `error` 字段就发现不了。相比 08-22 那种挂 7 小时的卡死，这种快速失败更容易被忽略。
- **已确认故障已恢复（08-24 上午实测）：** 代理 7897 现已正常监听、经它访问外网返回 200。但要注意——任务文档里约定给 `gh` 用的 10808 代理**今天没有启动**（连通性测试返回 000），本次补发改用可用的 7897 出网，**未改动任何脚本或配置**。
