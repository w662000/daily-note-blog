# 技术点 · LLM 调用参数（流式 / 推理）对延迟影响的析因实测方法论

> 对应项目轴 Handoff：`2026-08-04-handoff-5-模型测速-流式-stream-vs-推理-reasoning-双对比报告.md`
> 目的：从该项目提炼**可复用技术资产**——怎么设计一个干净的多因素对比实验来区分"哪个参数真正起作用、哪个是误归因"、怎么正确度量 LLM 接口延迟、怎么用实证反驳"凭印象下的结论"。下次要验证"参数 A 让 X 变快/变慢"这类命题，直接套这套 2×2 析因设计。

## 一、技术选型

| 选型项 | 选定 | 落选 | 依据 |
|---|---|---|---|
| 实验设计 | **2×2 析因（stream × reasoning 四组全组合）** | 单变量前后对比 | 单变量对比无法区分"stream 的功劳"和"reasoning 的影响"；析因能同时看主效应（T1，本项目正因此推翻了原帖结论） |
| 分组定义 | **N0 非流无推 / S0 流无推 / S1 流有推 / N1 非流有推** | "开/关某开关"两段描述 | 四组正交命名，任何两两比较都有明确语义（T1） |
| 度量指标 | **TTFT 首包延迟 + tot 总耗时 双指标** | 只看总耗时 | TTFT 反映"用户多快看到第一个字"，tot 反映"完整响应成本"；二者机制不同，必须分开（T1） |
| 采样纪律 | **每组 1 次、温和间隔、不重试** | 多次平均 / 重试 | 守限流红线；单次样本明确标注"仅供参考"，不把 ±20% 内差异当显著（T1） |
| 验证手段 | **解析客户端产物（app.asar）实锤** | 只靠接口测速 | 测速能证"快了"，但"为什么快"要扒客户端代码确认硬编码 `stream:true` 才闭环（T1） |
| 报告生成 | **脚本自动算百分比** | 手工填表 | 20 行数据手工算改善率必出错；`bench_report.py` 由原始 JSON 自动生成对比表（T1） |

## 二、实施要点与关键技术

1. **2×2 析因的核心价值是"分离两个变量"。** 原帖作者感知"去掉 reasoning_effort 变快了"，但本项目固定流式条件单独看推理效果、再固定推理条件单独看流式效果，最终证明：那 44.8% 的加速 100% 来自 stream，作者把 stream 的功劳误记到 reasoning 头上（T1，5 模型全印证）。

2. **TTFT 与 tot 的机制不同，结论可能相反。** 本实验结论：
   - **流式对 TTFT 普适大幅下降**：5 模型 TTFT 平均 ↓70%+（最快 ↓93.5%），与模型类型、是否带推理无关。
   - **流式对 tot 不一定降**：流式只是提前吐字、不减少总生成量；部分模型 tot 反而略升（流式返回了更多元数据/思考内容，字节数上涨）。
   → 只盯 tot 会得出"流式没用甚至更慢"的错误结论（T1）。

3. **`reasoning_effort` 只对"支持推理的模型"生效**（T1）：
   - 支持的（如 `gpt-oss-120b`、`deepseek-v4-flash`）：参数真实生效。最典型 `gpt-oss-120b` 非流式带推理首包暴增 +278%（要等推理完才返回），但**一旦开流式，首包几乎不受影响**（0.313→0.331s，边推理边吐字），只是 tot 因推理内容增加而上升。
   - 不支持的（如 `step-3.7-flash`、`glm-4.5-air`、`agnes-2.5-flash`）：服务端忽略该参数，`supportsReasoning=False`，所谓"带推理"只是生成量随机性，**不能归因于推理**。

4. **最佳组合是"带推理 + 流式"**：既享受推理质量，又不被首包延迟惩罚。这条结论直接解释了"为什么 WorkBuddy 出厂就该强制流式"（T1）。

5. **客户端硬编码实锤方法**（T1）：
   - 解析客户端安装包 `app.asar`（注意它比标准 asar 多 8 字节头部）；
   - 定位到对话入口逻辑，搜索 `stream:` 关键字：本项目在 `cli/dist/codebuddy.js` 找到**硬编码 `stream:!0`（true）共 14+ 处**，无任何非流式分支；
   - 5 处 `stream:!1` 全是内部基础设施（gRPC unary、编码协商、guardrail 默认值），不走用户对话。
   → 客户端层加 `stream` 字段既无效也不该加。

6. **已知偏差必须公开（影响读数）**（T1）：
   - **顺序偏差**：请求按 N0→S0→S1→N1 紧挨跑，S1 紧接 S0 可能命中服务端缓存，使部分 S1 的 TTFT 异常偏低。→ 读"带推理"那组对比时优先看 tot，TTFT 仅参考。
   - **单次采样**：每组仅 1 次，±20% 内差异不显著，只取大趋势。
   - **字节数 n 仅参考**：流式下 n 是 SSE 逐字节数（含 `data:` 前缀、usage 等元数据），非纯文本长度，n 暴涨不意味回答更长。

7. **报告由数据驱动不可手填**：原始数据存 `bench_5models_result.json`，脚本 `bench_report.py` 读它自动生成全部对比表与百分比，避免人工算错、也便于重跑（T1）。

## 三、模块职责划分

- **探针脚本（`bench_5models.py`）**：只负责按四组定义发请求、记录 TTFT/tot，产出原始 JSON。不做任何解读。
- **报告脚本（`bench_report.py`）**：只负责把原始 JSON 转成对比表与改善率，不做归因判断。
- **析因设计（人）**：只负责定义分组、约束采样纪律、选择度量指标——这是实验可信度的来源。
- **客户端产物解析（验证层）**：只负责把"接口现象"和"客户端实际行为"对上，完成因果闭环。
- **偏差声明**：作为报告的一部分，标注哪些读数不可全信，防止误用。

## 四、如何选型（可复用的决策方法论）

- **要证"A 导致 X"必须先排除"B 同时变了"**。当多个参数可能同时影响结果时，用 2×2 析因把每个参数的主效应单独隔离，比"我加了 A 然后变快了"可靠得多（T1，本项目正解）。
- **度量指标要选对机制**：延迟相关命题，TTFT（首包）和 tot（总耗时）是两种不同机制，缺一个都会得出片面结论。
- **单次采样的正确用法**：守红线前提下，单次样本只用以看"大趋势"，不用于做精细归因；要精细必须多样本平均，但多样本会撞限流红线——两害取其轻，本项目选趋势。
- **"客户端怎么调的"比"接口怎么传的"更根本**：接口层测出的现象，最终要用客户端真实行为（扒 asar / 读源码）来定案，否则可能"测出来快了但根本改不了"。
- **公开偏差不要藏**：顺序偏差、采样不足、度量口径这些限制，直接写进报告。隐瞒偏差会让别人把趋势当结论去改配置。

## 六、技术结合点

- **2×2 析因 + 双指标度量**：析因把变量拆干净，双指标把"快"的两种含义拆干净。两者结合才让"流式真有用、推理只看模型"这个反直觉结论立得住。
- **接口测速 + 客户端实锤**：测速证明"快了/没快"，扒 asar 证明"为什么"。只有前者，结论是悬空的；只有后者，结论没有现象支撑。
- **单次采样 + 公开偏差**：单次采样守住了限流红线，公开偏差守住了结论可信度。两者一起让"守红线"和"可复用"不冲突。
- **脚本生成报告 + 数据驱动**：原始 JSON 与报告脚本分离，实验可一键重跑、数据可审计。改了探针重跑一遍，整套对比表自动刷新，不依赖手抄。
- **顺序偏差 → 读 tot**：实测发现顺序会污染 TTFT 后，没有删数据，而是调整"读哪列"——这比重做实验更务实，也体现了"偏差可标注、可绕开"的工程态度。
