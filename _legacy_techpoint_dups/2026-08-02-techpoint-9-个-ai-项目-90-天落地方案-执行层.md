# 技术点 · 9 个 AI 项目 90 天落地方案（执行层）

> 对应项目轴 Handoff：`2026-08-02-handoff-9-个-ai-项目-90-天落地方案-执行层.md`
> 目的：把「一堆待办项目 → 可执行排期 + 可交付技术栈」这条链路里的**可复用技术资产**抽出来——并发度控制模型、交付技术栈、验收信号设计、合规约束的工程化落法。下次再面对「N 个候选项目要在有限周期内落地」时直接套用。

## 一、技术选型

| 选型项 | 选定 | 落选 | 依据 |
|---|---|---|---|
| 并发度控制模型 | **看板 WIP≤2**（2 个核心构建 slot） | 全并行推进 9 项目 | 2 人团队 + 单人多角色，超过 2 条构建线必然全部延期；副线单独限额每周 ≤8h，越线即砍（T1 实测排期结论） |
| 优先级模型 | **MoSCoW + Tier1/Tier2 分层** | 单纯打分排序 | 打分排序只给顺序、不给「砍不砍」；MoSCoW 的 Won't 档能直接出局，减少决策疲劳 |
| 判域方法 | **Cynefin** | 统一按「清晰域」做详细计划 | 混沌/复杂域项目做不出可靠甘特图，只能做探针 + 信号决策树 |
| 旗舰产品前端 | **Cloudflare Pages** | 自建 VPS + Nginx | 静态托管免运维、免费额度足；同账号可直连 Functions/D1（T1 已在 skillhub 项目实测上线） |
| 旗舰产品数据层 | **Cloudflare D1** | 自建 MySQL/Postgres | 单文件级 SQLite 语义 + 边缘读取，订单量级下无需独立数据库实例 |
| 临时文件存储 | **Cloudflare R2** | 本地磁盘 / 第三方对象存储 | 与 Pages/Functions 同栈，出网零费用；文档转换类产物本就是临时件 |
| 量化类项目数据源 | **AkShare** | 商业行情 API | 免费、覆盖 A 股研报/因子/选股；已在本机实测可用（注意接口分层，见第二节） |
| 收款通道 | 微信支付 / 支付宝（个体户「其他互联网服务」类目） | 年付订阅平台 | 需要短账期收现；年付订阅账期长且退款风险高，被一票否决规则排除 |
| 内容标识合规基线 | **GB 45438-2025 显式 + 隐式标识** | 只写免责声明 | 标识是强制项，免责声明替代不了（T0 标准文本） |

## 二、实施要点与关键技术

1. **第 0 周做「地基」，且必须一次性做完**：定双线 → 建通用免责库 → 开通收款 → 注册域名 → 立账本。地基没完成就开工，后面每个项目都会被同一件事阻塞一次（T1）。
2. **预算按「不可动用储备金」硬切一刀**：3 万拆成域名+小程序 1500 / API 年费 3000 / 获客 5000 / 建站 2000 / 法务 1000 / **储备金 1.3 万（锁死）** / 机动 500。储备金作为独立科目而不是「剩余」，才不会被逐笔蚕食（T1）。
3. **每个 Wave 结束挂硬验收指标**，且指标必须是付费转化而非流量：如「内测 10 人 ≥3 转化」「D30 前 ≥10 单」。非转化型指标（PV/注册数）不作为放行条件（T1）。
4. **Cloudflare D1 批量导入有硬上限，必须切分**：官方命令行工具会把大 SQL 文件当**单条语句**执行，撞上单条 10 万字节上限直接失败。正确做法是走 REST 批量接口 + **按字节切分** + 幂等插入（`INSERT OR IGNORE`）+ 断点续传。近 10 万行数据即靠这套导入完成（T1 实测）。
5. **本地看板要能「双击即用」，避开 file:// 跨域**：把 JSON 包装成 `window.SKILLS=[...]` 的 `.js` 文件，用 `<script>` 标签引入，绕开 `fetch` 在 `file://` 下的跨域限制（T1 实测）。
6. **量化类项目的数据源要按 host 分层挑接口**，不能整体判定「某库能不能用」：走东财 `push2` 系的 AkShare 接口在受风控环境下全挂（ProxyError / RemoteDisconnected），走 sina 系的 `stock_fund_flow_industry()` / `stock_fund_flow_concept()` / `stock_fund_flow_individual()` 直连可达。**结论：接口可用性判定粒度是 host，不是库**（T1 逐个实测）。
7. **合规约束要写成可执行清单，而不是段落**：不转售他人技能文件（IP + 服务条款双风险）、AI 生成内容按 GB 45438-2025 标识、不碰人脸/肖像、咨询类文案统一措辞「初步筛查建议，非法律意见」。每个项目落地页从同一份免责库取用，避免逐个手写产生口径漂移（T1）。
8. **流量入口与营收源分离**：免费检索站（`skillhub-cn.pages.dev`）只做交叉引流，**一旦加分销位或搬运内容即触条款与知识产权红线**，所以在架构上就不给它挂支付能力（T1 复审结论）。

## 三、模块职责划分

- **核心构建 slot A / slot B**：全周期只有两个，slot A 常驻旗舰产品，slot B 走接力（先短账期项目跑通收款闭环，再换下一个）。任何新项目要进来，必须先有一个出去。
- **副线层（Tier2）**：只承担「维系已有客户 + 补内容资产」的职能，每周工时上限 8h，不允许调用核心 slot 的时间。
- **通用免责库**：独立于所有项目的公共模块，被 9 个落地页引用，改一处全站生效。
- **免费检索站**：只承担引流职能，不承载交易、不承载内容分发。
- **账本**：独立科目化，储备金与运营金物理隔离，防止「先用后补」。
- **验收门**：挂在 Wave 边界上，是流程的一部分而不是项目内部环节——由 Wave 决定放不放行，项目自身无权跳过。

## 四、如何选型（可复用的决策方法论）

- **先设一票否决规则，再谈优先级**。本项目的三条硬否决：长账期（>30 天收现）/ 需资质门槛 / 需前置固定资产。任何候选先过这三道，过不了直接出局——比先打分再取舍省掉大量无效评估。
- **并发度是选型的一部分，不是执行细节**。确定「同时只能推 2 条」之后，9 个项目的排序问题会自动退化成「谁进 slot、谁接力」，比排 9 条平行甘特图简单一个量级。
- **技术栈按「同栈优先」选**。前端、函数、数据库、对象存储都收在同一云厂商内，省掉跨服务鉴权与出网费用；只有该栈明确覆盖不到的能力才外挂。
- **数据源选型以实测为准，不信元数据**。同一个库里不同接口的可用性可以完全相反，必须逐个跑一遍并记录 host 归属。
- **合规判断前置到选型阶段**。把「是否转售他人内容 / 是否触肖像权 / 是否需标识」放进筛选表，避免方案成型后被合规推倒重来。

## 六、技术结合点

- **一票否决 + MoSCoW + WIP≤2 是一条流水线**：否决规则把候选集砍到可评估规模，MoSCoW 排出层级，WIP 决定同时能推几个。三者缺一，要么评估爆炸，要么排完还是全并行。
- **同栈技术选型 + 免费流量入口**：Pages/Functions/D1/R2 同栈让「引流站」和「付费产品」共用一套部署与鉴权，引流站又反过来为付费产品提供零成本获客——但两者在权限与内容上必须隔离，才既复用基础设施又不踩条款。
- **验收门 + 储备金锁定**：Wave 验收门决定「继不继续投时间」，储备金科目决定「最多能亏多少钱」。前者控时间、后者控资金，两个闸门共同构成止损机制；只有其中一个时，项目仍会以另一种资源被拖死。
- **合规库 + 落地页模板**：免责文本集中化 + 落地页模板化，使得「新增一个项目」的合规成本接近于零，这是 9 个项目能并行铺开而不失控的前提。
- **接口 host 分层 + 降级链**：把数据源按 host 分层实测的结论，直接就是降级链的设计输入——知道谁会一起挂（同 host）才能选出真正独立的备用源。
