# 技术点 · 第三方 Skill 安装后静态审计

> 对应项目轴 Handoff：`2026-08-04-handoff-china-stock-data-安装扫描报告.md`
> 目的：从该项目提炼**可复用技术资产**——「从第三方源装了一个 skill / 插件 / 包，装完到底该查什么」的一套静态审计方法与检查清单。下次装任何来源不明的可执行资产，照这套流程走一遍再用。

## 一、技术选型

| 选型项 | 选定 | 落选 | 依据 |
|---|---|---|---|
| 分发渠道 | **SkillHub CLI**：`skillhub install china-stock-data --namespace kekewater` | 手动 clone / 复制目录 | 带命名空间与版本元数据，可追溯来源；手动拷贝无版本信息（T1） |
| 审计时机 | **装完立即静态扫描，跑之前** | 用出问题再查 | 硬编码凭据、非官方域名重定向这类问题一旦执行就已经外发请求了（T1，本项目正是扫描阶段发现的） |
| 审计方式 | **只读扫描 + 逐文件通读关键脚本** | 只看 SKILL.md 说明 | 说明文档不会写"我这里硬编码了别人的 token"（T1） |
| 版本真值来源 | **`_meta.json`** | `SKILL.md` frontmatter | 前者是发布平台写入的元数据，后者是作者手填、易与实际发布版本脱节（T1 推断） |
| 依赖判定 | **`requirements.txt` 核心/可选分层** | 一次性全装 | 可选依赖各自要账号、且部分会引发版本冲突（T1） |

## 二、实施要点与关键技术

### 审计清单（六查，按此顺序执行）

1. **查目录结构**——先建立整体认知，看清入口脚本、依赖声明、元数据、参考资料各在哪：
   ```
   china-stock-data/
   ├── _meta.json          (135 B)   版本元数据
   ├── SKILL.md            (13.9 KB) 技能说明（frontmatter 含 version）
   ├── requirements.txt    (565 B)   依赖清单
   ├── scripts/                      5 个 Python 脚本
   │   ├── china_stock.py     (28.4 KB) 主 CLI（16 个子命令）
   │   ├── news_aggregator.py (9.4 KB)
   │   ├── daily_briefing_image.py (9.8 KB)
   │   ├── stock_monitor.py   (3.8 KB)
   │   └── sec_edgar.py       (4.3 KB)
   └── references/                   6 篇 API 参考笔记
   ```
   **看文件体积能快速定位主干**：28.4 KB 的 `china_stock.py` 显然是要重点通读的那个。

2. **查版本一致性**——多处声明版本时必然会出现不一致：

   | 文件 | 字段 | 值 |
   |---|---|---|
   | `SKILL.md` frontmatter | `version:` | **2.0.0** |
   | `_meta.json` | `version` | **1.7.0** |

   本项目两者对不上。**处置原则：以平台元数据 `_meta.json` 为准**，不影响使用但要记录，否则后续报 bug 时说不清用的是哪版。

3. **查依赖分层**：
   - 核心必装：`requests / beautifulsoup4 / lxml / pandas(≥2.0) / openpyxl / pytdx / akshare(≥1.14.0)`
   - 可选（在 requirements 里被注释掉，各需账号）：`wencai / jqdatasdk / rqdatac / tushare`
   - **注意"注释掉的依赖"也是信息**：说明这些能力默认不可用，`status` 会报未安装，属预期而非故障。

4. **查子命令/入口全集**——把能被外部触发的入口全部列出来，并标注数据源与前置条件（本项目 16 个子命令 + 3 个辅助脚本各自的子命令）。**没被列进清单的入口，就是审计盲区**。

5. **🔴 查硬编码凭据**——本项目最关键的发现，`scripts/china_stock.py` 第 512 行：
   ```python
   TUSHARE_PRO = ts.pro_api('c8dbb3833192a3e47991b1975ad02d95a6567988826e519ba76b0ef5')
   ```
   一个 Tushare Pro token 明文写死随包分发，任何装此 skill 的人都拿得到。
   **判定它是问题而不是设计的依据是"内部不一致"**：同一个 skill 里，问财/聚宽/米筐/同花顺全都走环境变量或配置文件，唯独 Tushare 硬编码——**风格突变处即可疑点**，这个启发式比逐行读代码高效得多。
   建议改法：读 `TUSHARE_TOKEN` 环境变量，删明文。

6. **查凭据/账号矩阵**——把"每个能力需要什么、本机现在有没有"拉成一张表，这是后续排障的基准线：

   | 来源 | 配置方式 | 本机状态 |
   |---|---|---|
   | 通达信 TDX | 免 Key（需 pytdx） | ✅ 已装（沙箱出网被拦） |
   | 腾讯财经 | 免 Key | ✅ 可用 |
   | 同花顺 iFinD | `ifind_config.json`（access/refresh token） | ⚠️ 未配 |
   | AKShare | 仅 `pip install akshare` | ❌ 未装 |
   | iWencai 问财 | `WENCAI_TOKEN` | ⚠️ 未配 |
   | JQData 聚宽 | `JQ_USER`/`JQ_PASS` | ⚠️ 未配 |
   | Tushare Pro | **硬编码 token** / 应改 `TUSHARE_TOKEN` | ⚠️ 硬编码 |
   | RiceQuant 米筐 | `RQ_USER`/`RQ_PASS` | ⚠️ 未配 |

### 安装通道本身的坑（T1，来自当日日志）

- **SkillHub CLI 在 Git Bash / MSYS 下的两个路径坑**：① MSYS 的 `tar` 解析带盘符的 `C:` 路径失败；② 包装脚本收到 `/c/...` POSIX 路径后被当作相对路径拼成 `D:\c\...`。**修法：用 `cygpath -w` 统一转成 Windows 原生路径再传入。**
- **托管 pip 的 safe-delete**：默认把卸载文件移入回收站，沙箱环境无回收站 → 直接 `SAFE_DELETE_FAIL_CLOSED` 中止安装。需给 pip 单独开沙箱豁免。

### 审计结论的处置红线

**扫描出问题 ≠ 可以直接改**。修改已安装产物属于"重写"类操作，必须先把发现和建议交给用户、拿到明确授权再动手（本项目正是先出报告问"是否要我改成读 `TUSHARE_TOKEN`"，授权后才执行）。

## 三、模块职责划分

- **元数据层（`_meta.json` / `SKILL.md` frontmatter）**：声明身份与版本，是"这是什么"的权威来源。审计时用于交叉验证。
- **说明层（`SKILL.md` 正文）**：声明触发词与用法。**审计时视为"作者的主张"，不是事实**——本项目里它写的脚本路径就是错的。
- **依赖层（`requirements.txt`）**：声明运行前置。审计时用于评估安装副作用（体积、版本冲突）。
- **执行层（`scripts/`）**：真正会发起网络请求、读写磁盘的部分。**审计权重最高，凭据与外发地址只可能藏在这里。**
- **知识层（`references/`）**：作者沉淀的外部接口笔记。审计时是加分项——有这层说明作者真跑过，可信度上调。

## 四、如何选型（可复用的决策方法论）

1. **第三方可执行资产一律"先扫后用"**：来源可信度越低，扫描越要前置到执行之前。已执行过再扫，凭据外发这类事已经发生了。
2. **判断"版本以哪个为准"**：平台生成的元数据 > 作者手填的 frontmatter > README 里的文字描述。写入方越自动化，越可信。
3. **发现可疑代码时先看"是否与自身设计一致"**：同一项目里 7 个源走环境变量、1 个源硬编码，这个不一致本身就是最强信号。比逐行审计省时。
4. **依赖装不装的判据**：核心依赖直接装；可选依赖看"它解锁的能力我现在用不用得上"，以及"它会不会拉低已装包的版本"。本项目的 `jqdatasdk` / `rqdatac` 就会把 pandas 降版拖累 akshare。
5. **审计产物要落成一张凭据矩阵**：不是为了好看，是为了下次 `status` 报某源不可用时，能一眼看出是"没配"还是"配了但坏了"。

## 六、技术结合点

- **目录结构 + 文件体积**：两者结合能在读第一行代码之前就锁定审计重点（28.4 KB 的主 CLI vs 3.8 KB 的监控脚本，投入产出比差一个量级）。
- **凭据矩阵 + `status` 自检命令**：矩阵是静态的"应该是什么"，`status` 是动态的"实际是什么"。两张表对照，任何配置问题都能秒定位到具体源。
- **"风格一致性"启发式 + 逐行审计**：先用一致性扫出可疑点（Tushare 是唯一硬编码的），再对可疑点做逐行精读。全量精读 28 KB 代码不现实，这个组合把成本压到可接受。
- **审计报告 + 授权红线**：报告负责"把问题讲清楚"，红线负责"不越权动手"。两者配合，既拿到安全收益又不破坏用户对安装产物的控制权——只出报告不修是空转，不问就改是越界。
- **版本不一致记录 + 后续排障**：单看这条只是"小瑕疵"，但和"上游接口会漂移"结合起来就有价值了——报 bug、查改动、判断某个函数在哪版被移除，都要先确定自己用的是哪版。
